## 1. Bugs

**Bottom line.** The engine is solid: across edge-case files, config fuzzing, stat invariants (a box score adds up to its game log, makes never exceed attempts), XSS probes in every tab, a run-to-run determinism check and a warm-vs-cold check of every setting, only one engine defect turned up (B4). The serious bugs are in the page's state handling around the engine. Locks leak between files and are wiped when the user switches files. The drawn seed is never saved, so "Restore last session" brings back a different class. Several actions can't be fully undone, and dropping files together with a universe export silently throws away the import's own record of the world. The test suite (`node tools/test-parallel.js --fast`) passed: 1918 checks in 38 jobs, no failures.

Method: Node harnesses (scripts in `scratchpad/s1/`) plus headless Chromium driving the real page over HTTP. "VERIFIED" means I reproduced it.

### B1. Switching the active file deletes every lock, with no undo — High — VERIFIED
**Where:** `js/app.js:4832-4848` (`checkLockFingerprint`), `js/app.js:5229-5242` (the `#fileSelect` change handler), `js/app.js:4680` (`installFiles` resets `state.active` to 0).
**Repro:** Load two classes. Lock a player in file 0. Choose file 1 in the file picker, then choose file 0 again. `App.state.overrides` is `{}` both times, and the Undo button reads plain "Undo". The same thing happens after a reload: the files load with file 0 active, so locks made on file 1 are dropped.
**Cause:** Locks are one global map with one `overrideFingerprint`. Whenever the active file's fingerprint differs, `checkLockFingerprint` treats the locks as "from a different draft class" and sets `state.overrides = {}`. It does this on an ordinary file switch, without `pushUndo`.
**Fix:** Key locks by file fingerprint (`state.overrides[fp][key]`), the way notes are scoped with `userKey`. Until then, stash the locks on a switch and bring them back when the user returns to that file, instead of deleting them. Never drop locks without an undo entry.

### B2. Other files are simulated with the active file's locks, matched by pid — High — VERIFIED
**Where:** `js/app.js:5317-5320` (`effectiveCfg` always sets `cfg.overrides = state.overrides`), `js/app.js:5660` (`ensureResult`), `js/app.js:11209` (`exportAllZip`), `js/app.js:11131` (`exportAll`), `js/app.js:11748` (`mergeInto`).
**Repro:** Load files A and B, which use the same pids. Lock pid 0 in A at ovr 72. Run "Export all (zip)". In B's result, pid 0 has `newOvr 72` and `override {ovr:72}`; without the lock he is 51.
**Cause:** `ensureResult(i)` runs every non-active file with `effectiveCfg()`, and that config carries the active file's locks. This is the cross-class pid mis-lock that `checkLockFingerprint` exists to prevent. It reaches Export all, the zip, and merging several classes into a league.
**Fix:** In `ensureResult(i)` / `fileCfgFor(i)`, pass `overrides` only when `i === state.active`, or when `state.overrideFingerprint === state.files[i].fingerprint`. Otherwise pass `{}`. Per-file locks (see B1) fix both bugs.

### B3. "Restore last session" (and any reload) restores a different class — High — VERIFIED
**Where:** `js/app.js:372-440` (`payload()` has no `lastSeed`), `js/app.js:5943` (`writeHash()` is called without the drawn seed), `js/app.js:8270-8300` / `8346-8395` (the session save and restore).
**Repro:** Load a class and press Reroll. The pill shows `seed 299586135 · 185cku`. Reload and click "Restore last session". The pill now shows `seed 216976213 · 8awv5c`: same files and settings, different class.
**Cause:** A reroll blanks `cfg.seed` and keeps the drawn seed only in `state.lastSeed`. That field is not in the persisted payload, the IndexedDB session snapshot, or the address-bar hash, so every restore draws a new random seed.
**Fix:** Persist `lastSeed` in `payload()` and read it back in `restore()`, or let `saveSessionNow` write `encodeConfig(true)`'s seed. Also consider `writeHash(true)` so a reload with the same file keeps the class.

### B4. `efficiencyEnv` is not declared for the scoreboard phases, so a re-run after changing it leaves old game scores — High — VERIFIED
**Where:** `js/engine.js:5017-5045` (the `regular` and `postseason` deps lists); `js/teams.js:1671-1699` (`pointsPerPair` → `efficiencyScale(cfg)` reads `cfg.efficiencyEnv` inside `playGameScore`).
**Repro:** `scratchpad/s1/warm.js` tries every setting at an off-default value, comparing a re-run on a cached runner ("warm") with a fresh run ("cold"). Only `efficiencyEnv` differs: `MISMATCH efficiencyEnv 3 fb83d2711f (warm) 77bb472524 (cold)`.
**Cause:** `efficiencyEnv` is listed only for the `stats` phase. Moving the slider re-runs stats onward, but the regular-season and March scoreboards (team points, W-L, possibly the champion) stay at the old efficiency. The box score is anchored to those stale points. The class on screen and its export no longer match what the same seed and settings give in a fresh run, the CLI or a shared link.
**Fix:** Add `"efficiencyEnv"` to the `regular` and `postseason` deps. Better still, derive the deps from what each phase actually reads, or add the warm-vs-cold sweep to CI so it covers every setting.

### B5. Importing a universe together with its class files cancels the replay and discards the import's own record of the world — High — VERIFIED
**Where:** `js/app.js:4521-4531` (`readFiles` installs the classes, which starts a run, then calls `importUniverse`); `js/app.js:8625-8639` (`importUniverse` calls `installFiles(loaded, problems)` for embedded files without `noRun`); `js/app.js:4727`; `js/app.js:5873-5882` (`runNow` cancels and restarts a running chain); `js/app.js:7296` (the `universeReplay` gate is only set for multi-run replays).
**Repro:** I tampered `world.json` so season 2026 says "Fake U". Load the three classes first, then import it: the result is `2026 Fake U (restored)`, as designed. Drop the three classes and `world.json` together, or import a with-classes export (always the case for "Export with class files"): the status reads "Settings changed — restarting the universe…", then "Universe stopped: 1 seasons", then a fresh chain. The rows come out `2026 Michigan State`, with no divergence reported and nothing restored.
**Cause:** `installFiles` schedules `run()` two animation frames later. By then `importUniverse` has started the replay chain, so `runNow` sees `universe.running`, sets `universeCancel`/`universeRerun`, and replaces the replay with a plain cold chain. The cancelled replay clears `universeExpect` and `universeImported`. Multi-run (extend/resume) plans are flattened into one cold run, and `createdAt` is lost.
**Fix:** Call `installFiles(..., {noRun: true})` in both import paths. In `readFiles`, skip `installFiles`' run when a universe export is in the same drop. Also make the `runNow` restart path a no-op while `state.universeExpect` is set.

### B6. A failed or cancelled "Reroll until…" changes the class on screen, says it didn't, and can't be undone — Medium — VERIFIED
**Where:** `js/app.js:6340-6341` (`rememberSession(); rememberPool();` before the search), `js/app.js:6334-6339` (`unwind`), `js/app.js:6384-6391` (`cancel`), `js/app.js:6432-6451` (`finish`).
**Repro:** Load a class (pill `264819867 · 1vyfi0`) and run `App.rerollUntil(["topOvr:99"], 2)`. Status: "No class in 2 tries satisfied… The class on screen is unchanged…". Pill afterwards: `264819867 · 10b825`. Same seed, different class. `poolHistory` went from empty to one entry.
**Cause:** `rememberPool()` pushes the on-screen class's build pool into `state.poolHistory`, which feeds `recentPools`, an input to the build phase. A failed or cancelled search calls `unwind()`, which removes the undo entry but leaves the pool memory changed. The `run()` that "restores" the class then rebuilds it against a different memory.
**Fix:** Save `poolHistory`, `anomalyHistory` and `flavorHistory` before the search and put them back in `unwind()`. Or call `rememberPool()` only once a seed has been found and is applied.

### B7. Undo, run history and kept classes don't save mutators, challenge state, the dynasty or the universe — Medium — VERIFIED (mutators, challenge)
**Where:** `js/app.js:783-848` (`undoSnapshot` / `setSnapshot`); callers at `2777` (mutators), `6713-6721` (`startChallenge`), `7922-7926` (`startDynasty`), `8184` (`loadUniverseSlot`), `7620` (synthetic universe), `8668/8692` (`importUniverse`); `rememberSession` at `6039` and `keepCurrentClass` at `4942` use the same snapshot.
**Repro (Chromium):**
- Tick a mutator in the replay dialog, then click "Undo: changed the mutators". `state.mutators` is still `['no-bigs']`.
- Run `startChallenge(CHALLENGES[0])`, then Undo. `state.challenge` is still `'cinderella'`. `effectiveCfg` keeps wiping the pool, anomaly and flavor memories, so the "restored" class can differ from the original.
**Cause:** The snapshot holds cfg, locks, seed, the pool/anomaly/flavor memories and per-file patches only. `state.mutators` changes how `effectiveCfg` builds the class but is not in it, so a run-history entry or kept class made with mutators on does not reproduce. Undoing "loaded a saved universe" or "started a dynasty goal" restores the settings but not the universe or the goal.
**Fix:** Add `mutators`, `challenge`/`replayRun` and (by reference) `universe`/`dynasty` to `undoSnapshot` and `setSnapshot`. Where a step can't be undone, don't push a labelled undo entry.

### B8. Merging into a league: added players keep relative pids that now point at strangers — Medium — VERIFIED
**Where:** `js/engine.js:9120-9145` (the "append" branch of `mergeIntoLeague`; `copy.pid = ++maxPid` at 9131).
**Repro:** Make a class with pids 100+ where 100 and 101 are brothers, and merge it into a league whose pids run 0-129. The appended player (new pid 130) still has `relatives: [{pid:101}]`. League pid 101 is "Lg P101", an active player on team 1.
**Cause:** Appended players get new pids, but `relatives` is copied unchanged and never remapped or trimmed. A file-only export does cut dangling relatives (`exportFile`, 8209-8231); the merge path doesn't.
**Fix:** While appending, build an `oldPid → newPid` map, remap `relatives[].pid` through it after the loop, and drop any entry whose pid isn't in the map.

### B9. "Copy command line" drops settings pinned at their default, so the CLI builds a different class — Medium — VERIFIED
**Where:** `js/share.js:181` (`NOT_FLAGS` includes `pinned`) and `186-201`; `js/app.js:3984-3986` (`encodeConfig` puts `pinned` in the payload); `js/engine.js:1354-1358` (`userTouched`).
**Repro:** `Share.commandLine({delta:{seed:"s1", pinned:["pace",…]}})` gives `bbgmdraft run c.json --seed s1` with no note. The page config (`pinned:[pace,upsetFactor,injuryRate,statNoise,scoringEnv]`) and the CLI config differ for seeds s1, s2 and s3: export hashes differ, and effective pace is 67.6 vs 64.6 for s1.
**Cause:** Touching a control pins it even when it is back at its default, and storylines and flavors leave pinned settings alone. The command line only writes `--set` for settings that differ from the default, so the pin is lost and the CLI lets a storyline bend that setting.
**Fix:** For each pinned-at-default key, emit `--set key=<default>`. The CLI's partial-object rule in `Config.make` already pins any key it is given. Otherwise print a note naming the pins and suggesting `--settings`.

### B10. CLI `--locks` silently ignores the rename, size and rating columns the page writes — Medium — VERIFIED
**Where:** `js/engine.js:8349-8402` (`planLockCsv` reads only key, name, ovr, pot, archetype and college); the page's export is `js/app.js:4581-4582` (it adds `newname`, `hgtinches`, `weight` and 15 rating columns); the CLI caller is `bin/bbgmdraft.js:260-272`.
**Repro:** A page-format CSV whose rows lock only a new name and height, or a rating, returns `{"applied":[],"unmatched":[],"rejected":[],"total":2}`. The CLI reports "0 of 2 row(s) applied" and nothing else.
**Cause:** There are two parsers. The page uses `Views.planLockRows`; the CLI uses the older `Engine.planLockCsv`. A row whose only locks are in the extra columns builds an empty patch and is skipped (`continue`) without being counted anywhere.
**Fix:** Move `planLockRows` into a module both sides load (engine or share), so there is one parser. At minimum, report recognised-but-unsupported columns and rows with an empty patch.

### B11. Settings-file import drops the mutators its export writes — Medium — VERIFIED
**Where:** `js/app.js:4542-4565` (`settingsJson` writes `cfg.mu`; `applySettingsJson` passes it to `CFG.make` and never sets `state.mutators`).
**Repro:** `Config.make({mu:['no-bigs'], …})` keeps `mu` as an unknown key (checked in Node). `applySettingsJson` never reads it, so loading the file keeps the current mutators and stores a stray `state.cfg.mu`.
**Cause:** `applyLinkPayload` (4206) handles `mu`, but this path was never updated to match.
**Fix:** Do what `applyLinkPayload` does: `state.mutators = ReplayMeta.cleanMutators(cfg.mu); delete cfg.mu;` before `CFG.make`.

### B12. Copying a link breaks the next Back press — Low — VERIFIED
**Where:** `js/app.js:4093-4096` (`setHash` → `history.replaceState(null, …)`), reached from `copyLink` (`4137`) and the async compressed-hash callback (`4131`).
**Repro:** Open a player page and call `App.copyLink()`; `history.state` is now `null`. Open a team page, then press Back. The app stays on the team page (`{team:"Abilene Christian", tab:"teams"}`) while the URL changes.
**Cause:** `replaceState(null, …)` erases the `bbgmNav` state that `syncNav` wrote. The popstate handler then returns early on `!st`, and no `render()`/`syncNav` follows `copyLink` to write it back.
**Fix:** Keep the current state: `history.replaceState(history.state, "", hash || "#")`.

### B13. A compressed ("lean") link drops `fp` but keeps tab/prospect/compare, so the deep link is refused with a false message — Low — VERIFIED
**Where:** `js/share.js:113-117` (`encodeLink`'s lean pass) and `js/app.js:4122-4125` (`writeHash`'s lean pass); `js/app.js:4216-4229` (`applyPendingDeep`).
**Repro:** Encode a payload with 400 locks, `fp`, `tab:"compare"`, `pk` and `cmp` at a small limit. The decoded result gives `readDeep` → `{…,"fp":null}`, and `deepApplies(d,"abc123")` → `false`. The recipient sees "This link names a tab or a prospect in a different class file" on the same file.
**Cause:** `fp` is dropped together with `overrides`, but it also identifies the deep fields.
**Fix:** Drop `fp` only if no `tab`/`pk`/`cmp` remain, or drop those deep fields too.

### B14. The service worker deletes every cache on the origin, not just its own — Low — UNVERIFIED
**Where:** `sw.js:35-38` (`keys.filter((k) => k !== CACHE).map(caches.delete)`).
**Cause:** On activate, every Cache Storage entry except `bbgm-draft-workshop-v2` is deleted. On a shared origin (e.g. `user.github.io/<repo>/`, which `scope: "./"` in the manifest suggests), that wipes other apps' offline caches.
**Fix:** Delete only caches whose names start with `bbgm-draft-workshop-`. Optionally put the copy-to-cache `put` inside `e.waitUntil` so it can't be dropped when the worker stops.

### B15. Some CSV exports skip the spreadsheet-formula guard — Low — VERIFIED
**Where:** `js/share.js:303-306` (`csvCell` used by `contactCsv`, the batch contact sheet at `app.js:12097`); `bin/bbgmdraft.js:351-355` (`csvCell` for `batch --csv` and `mock --csv`).

### B17. A search's result can be applied after the mutators changed — Low — UNVERIFIED
**Where:** `js/app.js:6314-6317` (`untilKey` covers cfg, locks, active file, per-file patches and files, but not `state.mutators`); `apply()` at `6403-6431`.
**Cause:** Toggling a mutator during a "Reroll until…" search (in the worker) doesn't invalidate it. The found seed is then applied under different mutators, and the status still says it "satisfies" the conditions.

### B18. Almanac Markdown/print: names aren't Markdown-escaped, and dotted abbreviations get two periods — Low — VERIFIED
**Where:** `js/almanac.js:240, 258, 82` (`"…" + name + "._"`), and `inline()` / `renderBody` at `613-680`.
**Repro:** A player named `_a_ \`b\` [c](#d) **e**` comes out as italic, code, an in-page link and bold in the printable HTML. HTML is escaped, so this is not XSS. A seed list ending in `N.J.I.T.` gives `N.J.I.T.._`. In the `.md` download, names containing raw `<img …>` are written verbatim.
**Fix:** Escape `\ * _ [ ] \`` (and `<`) in names before they go into the Markdown. Use `Text.endSentence` for the closing period.

### B19. `mock --rounds` and the page's rounds option are ignored for a league file — Low — UNVERIFIED
**Where:** `js/pro.js:361-377` (when `opts.league` gives a plan, `rounds` is unused); `js/pro.js:285-311` (`leagueDraft` takes its rounds from the league's picks, defaulting to 2); CLI `bin/bbgmdraft.js:649-656`.
**Cause:** A `--rounds 3` mock of a league class silently returns the league's two rounds.
**Fix:** Pass `rounds` through to `leagueDraft` (cap the generated rounds and trim `slots` by round), or warn when it is ignored.

### B20. Merge silently leaves out classes that haven't run — Low — UNVERIFIED
**Where:** `js/app.js:11749-11754` (`if (r) results.push(...)`); `ensureResult` returns `null` in universe mode before the chain has recorded a file (`5655`).
**Cause:** A multi-class merge started during or after a reload of a universe writes a league with only some of the chosen classes, and the success message lists only those seasons. Nothing says which classes were skipped.
**Fix:** Refuse (or name the skipped files) when `ensureResult(i)` returns `null` for a selected class, as `exportAllZip` already does.

### B21. The daily seed uses local time, and the achievement ledger uses UTC — Low — VERIFIED (code)
**Where:** `js/app.js:2560-2564` (`dailySeed`, local date), `js/replay.js:33-37` (`dateKey`, local), `js/app.js:2714` (ledger `toISOString().slice(0,10)`, UTC).
**Cause:** "The same class for everyone on the same date" holds only within one time zone: at any given moment users in different zones get different daily seeds. Near midnight, the ledger also stamps a different date from the daily that was played.
**Fix:** Derive the daily key from the UTC date everywhere (or document it as local), and use the same clock for the ledger.

## 2. UI/UX and QOL

**Bottom line.** The basics are sound in the default light and dark themes: focus rings show on every control, the tab bar is a proper roving `tablist`, status messages go to an `aria-live` region, there is an Escape/`?` shortcut sheet, and the default themes pass AA contrast. The big problems are about time and scale, not polish.

1. **Long jobs give almost no feedback.** A 57 MB league freezes the page for 11–17 s, the first sample class for about 10 s, and a merge into that league for 23.5 s. During each one the only sign of life is a one-line status ("Reading 1 file…", "Generating the class…", "Merging into …"). There is no percentage, no phase, no file size and no cancel.
2. **The draft board cannot answer "who is the best at his position".** It has no recruiting-stars column and no positional rank. Its position filter matches exactly, so "G" leaves out PG and SG. A 2–3-star prospect who is the top player at his position looks exactly like any other mid-board row.
3. **Phone layout breaks in a few places.** The board's Ovr and Pot columns sit off-screen, the Mock draft page scrolls sideways, and achievement toasts cover content and the Settings button.

Method: served the repo with `python3 -m http.server` and drove it with Playwright and Chromium at 1440×900, 820×1180 and 390×844, in light and dark. I took about 60 screenshots, ran a computed-contrast walk over all 8 themes, an accessible-name and label sweep of every tab, keyboard Tab walks, and a timed load of a synthetic 56.7 MB league export (6,210 players, 3 future classes), both as `.json` and as `.json.gz` (11 MB). Scripts and screenshots are in `scratchpad/s2/`.

### Needed fixes

**U1. Loading a large BBGM file: no real progress indication, and the page freezes**
- *Problem.* The user sees "Reading 1 file…" in small text under the drop box, and the box's border turns dashed brown. Then the main thread blocks with no repaint:
  - 2.5 s for parse and split (3.7 s for the `.gz`);
  - then 8.7 s for the 56.7 MB `.json` and 13.7 s for the `.gz` under "Generating the class…";
  - then a further 1.7–3.2 s after the board appears.
- There is no byte count, no percentage, no file size, no phase name and no cancel. A real BBGM league can be several times larger.
- *Where.* `js/app.js:4467` `readFiles` (one `setStatus` line), `:4352` `readTextFile` (`arrayBuffer()` all at once), `:5768` `withBusy` → `runNow`.
- *Evidence.* VERIFIED in Chromium:
  - MutationObserver log: `161ms Reading 1 file…` → `3088ms Generating the class…` → `MAIN THREAD BLOCKED 8702ms` → `MAIN THREAD BLOCKED 3228ms`.
  - Screenshots `load-0.png` and `load-done.png`.
- *Fix.*
  - Add a progress overlay, or a progress bar inside the drop box, with named phases: Reading (x of y MB, from `f.stream().getReader()` counted against `f.size`) → Decompressing → Parsing → Splitting into N classes → Simulating class 1 of N.
  - Use a CSS `transform` spinner. Compositor animations keep moving while the main thread is busy.
  - Move `JSON.parse` and `draftClassesIn` into `js/worker.js` when a Worker exists, keeping the main-thread fallback for `file://`.
  - Yield between engine phases so the status can say which phase is running.
- *Effort.* M (overlay and phases) / L (worker parse).

**U2. Downloading a large file (merge into a league): a 23.5 s freeze, a result that vanishes, and an uncompressed output**
- *Problem.*
  - Merging 3 classes back into the 56.7 MB league blocked the main thread for 23.5 s with only "Merging into league-big.json…".
  - The success line then auto-hides after 3.5 s (`setStatus` is not sticky).
  - The output is always plain `.json` (57 MB+), even when the source was a `.json.gz`. The universe export already gzips with `CompressionStream` (`app.js:7798`).
- *Where.* `js/app.js:11748` `mergeInto`, `:11782` `startMerge`, `:10224` `download`, `:10196` `setStatus`.
- *Evidence.* VERIFIED: `download after 25075 ms`, `BLOCKED 23545`, screenshot `merge-after.png`.
- *Fix.*
  - Show a busy overlay with the steps (building → serializing → compressing → saving).
  - Write `.json.gz` when the source was gzipped, or offer it as a choice.
  - Make the result sticky and include the file size ("Wrote X.json.gz, 11.2 MB").
- *Effort.* M.

**U3. First run: "Try a sample class" freezes the page for about 10 s**
- *Problem.* A first-time visitor's first click blocks the page for 10.1 s. The only feedback is "Generating the class…", and it cannot animate. The first thing that follows is an "Achievement: strangeness 54/100" message (see U9).
- *Where.* `js/app.js:4604` `loadSample` → `run` → `runNow`.
- *Evidence.* VERIFIED: `241ms Generating the class…` → `10276ms BLOCKED 10125`.
- *Fix.* Report phase progress by yielding between runner stages (e.g. "Simulating the season… 3/7"). Show the class table from the cheap phases first and fill in the season afterwards. At minimum, show a spinner that keeps animating (U1).
- *Effort.* M.

**U4. A low-ranked (3–4 star) prospect who is the best at his position is not discoverable on the board**
- *Problem.*
  - The board has 13 fixed columns (`Board, Rd, Pick, Player, Pos, Year, Ovr, Pot, School, Preseason, ±, PPG, Honors`). None of them is recruiting stars or a positional rank, and nothing marks "top SF in the class".
  - The ★ stars column exists only in Player Edit, and it is off by default.

## 3. Large files and general robustness

**Bottom line.** A BBGM league file goes through four copies held at the same moment: the compressed bytes, the decompressed bytes, a whole-file string, and the parsed object. That puts peak renderer memory at about **5x the JSON size**. The main thread stays blocked from the moment the file is dropped until the split classes appear, and the only feedback is the line "Reading 1 file…". There is no progress and no way to cancel.

A file of **536,870,888 characters or more (about 512 MiB of JSON) cannot be opened at all.** Chromium's `TextDecoder` quietly returns `""` and the user is told "Unexpected end of JSON input".

Two more costs land after the load:

- **Session autosave:** it stringifies the whole league on the main thread just to compare it with a 60 MB cap. On a 500 MB league that is a 26.7 s freeze, and the renderer peaks at 4.27 GB.
- **Merge:** it writes an uncompressed `.json` that is 6–7.5x the `.gz` the user dropped.

**Measurements.** Headless Chromium 141 drove the real page (the `#file` input, the merge through the Export menu). The renderer's RSS was sampled every 200 ms from outside, and JSON.parse, JSON.stringify and TextDecoder were wrapped to time them. The test files are synthetic BBGM exports (`s3/gen.js`) with the real top-level stores: `players` with inline `ratings`/`stats`/`face`/`transactions`, `teams`, `teamSeasons`, `teamStats`, `games` box scores, `events`, `draftPicks`, `schedule`, `playoffSeries`, `awards` and the small stores. Each has three future draft classes of 75 prospects with `tid: -2`. Names include non-Latin-1 letters, as real leagues do, so decoded strings take **2 bytes per character**.

A prototype of the proposed design (`s3/selective.js`) works like this:

- It scans the bytes once to index the top-level stores and parses only the 9 keys the tool reads.
- On merge, it copies the untouched stores' raw bytes around a re-serialized `players` array and streams the result through gzip.

On L200 the retained heap fell from **311 MB to 65 MB (4.8x less)**. Load-to-classes time fell from **15.8 s to 4.2 s**. The output is a **27.3 MB `.json.gz` instead of 213 MB**. The output was checked: its `players` match an in-memory merge exactly, and its `games` and `events` match the input exactly.

Validating, splitting and merging are cheap. **Nearly all of the cost is the whole-file string, the parse and the stringify**, and that is where the fixes below aim.

### L1. A hard 512 MiB ceiling, reported as a corrupt file
**VERIFIED.**
- **Where:** `js/app.js:4352-4377` (`readTextFile`) and `:4493`; `bin/bbgmdraft.js:99-101` and `:467-470`.
- **What happens:**
  - V8 caps a string at 0x1fffffe8 = 536,870,888 characters.
  - In Chromium 141, `new TextDecoder().decode()` of 560 MB returns **an empty string without throwing**. Checked with `s3/strlim.js`: `decodeLen: 0`, while `Response.text()` fails with "Failed to fetch".
  - `JSON.parse("")` then throws, so dropping L560.json.gz shows **"L560.json.gz: Unexpected end of JSON input"** after 8.8 s and a 2.9 GB peak.
  - The CLI prints "Cannot create a string longer than 0x1fffffe8 characters".
- **Who hits it:** real long-running leagues with box scores kept are in this range (the brief says 50–500 MB).
- **Fix, quick:**
  - Predict the size before doing anything. For a `.gz`, the last 4 bytes (gzip ISIZE) are the uncompressed size; this was checked exact on all four test files. For a plain file, use `File.size`.
  - Above about 500 MB, say plainly: "This league is 560 MB unpacked; browsers cannot hold one text that large. Re-export without box scores/events, or use …". Until L3 exists, that sentence can stop there.
  - Treat `text.length === 0 && bytes > 0` as this case, not as bad JSON.
- **Fix, real:** L3. The selective path never builds a whole-file string, so the ceiling goes away.
- **Effort:** S for the message; the real fix comes with L3.

### L2. Four whole-file copies at once: peak is about 5x the JSON size
**MEASURED.**
- **Where:** `js/app.js:4359-4377`.
- **What happens:** the steps that hold the whole file are:
  - `f.arrayBuffer()` holds the compressed bytes.
  - `new Response(stream).arrayBuffer()` gathers the decompressed chunks and then concatenates them.
  - `TextDecoder` produces a two-byte string of 2 x the JSON size.
  - `JSON.parse` builds the object.
  - All of this happens inside one promise chain, so the earlier copies are still referenced while the next one is built.
- **Measured peaks (renderer):** 1,086 MB for 213 MB of JSON (5.1x); 2,704 MB for 524 MB (5.2x).
- **Consequence:** an 8 GB laptop with other tabs open, or any phone, cannot open the 500 MB case at all.
- **Fix:** comes with L3. As a stop-gap, decode in one streaming pass with `stream.pipeThrough(new TextDecoderStream())` into parts, and drop `raw` before parsing. That removes one of the four copies but not the string.
- **Effort:** S as a stop-gap.

### L3. The whole league is parsed when the tool reads 9 keys
**MEASURED / VERIFIED.**
- **Where:** `js/app.js:4493`; consumers in `js/engine.js:548-1020` and `js/pro.js:238-296`.
- **What the tool reads:** `players`, `teams`, `teamSeasons`, `draftPicks`, `gameAttributes`, `startingSeason`, `version`, `meta` and `bbgmdraft` (the last two only for passing through and stamping). Every other store, including `games`, `events` and `teamStats`, is used only to be written back out by the merge.
- **How much is unused:** in the test files those stores are **61% of L50 and 77% of L200** by bytes (`games` alone is 115 MB of 213).
- **Design:**
  1. In a worker (L4), stream the file: `file.stream()`, then `DecompressionStream`, then a byte scanner that tracks depth, strings and escapes. The scanner records each top-level key's byte range, and keeps (or parses on the fly) only the needed stores. The prototype scanner runs at the same throughput as `JSON.parse` (0.5 s for 52 MB, 2.5 s for 213 MB here).
  2. For `players`, go one level further: parse one element at a time and yield to the event loop between chunks. This allows progress reporting and sidesteps the string ceiling, because no slice is larger than one player.
  3. Keep **the `File` handle and the store index**, not the parsed league. A merge re-streams the file (see L6).
- **Measured gain (Node, L200):** heap 311 MB → 65 MB; time from load to classes 15.8 s → 4.2 s. On L50: 82 MB → 33 MB and 1.8 s → 1.3 s.
- **Effort:** M. The scanner is about 60 lines (`s3/selective.js`, `indexTop`). Per-element parsing of `players` adds about 40.

### L4. Main-thread blocking, no progress, no cancel
**MEASURED.**
- **Where:** `js/app.js:4467-4531`. Only the batch and search paths (`js/worker.js`) use the worker.
- **Measured freezes (longest gap between frames during load):** 1.0–2.1 s for L50, **8.7 s for L200, 17.7 s for L500**. Chromium shows "Page Unresponsive" after about 5 s.
- **What the user sees meanwhile:** the status "Reading 1 file…" for the whole time, nothing that says how far along it is, and no way to stop. A wrong 500 MB file can only be escaped by closing the tab.
- **Design:**
  - Post the `File` to `js/worker.js` with a new message type `"readLeague"`. Structured-cloning a `File` is cheap because it is a handle.
  - The worker pipes `file.stream()` through a counting `TransformStream`, then `DecompressionStream`, then the L3 scanner.
  - Every chunk, it posts `{type:"readProgress", phase:"unpack"|"players"|"split", bytesRead, total: file.size, unpacked, unpackedTotal: ISIZE}`.
  - The page draws a determinate bar ("Unpacking 18.2 / 28.6 MB … reading players 2,100 / 4,355"). A Cancel button calls `worker.terminate()`, or `reader.cancel()` in the fallback.
  - **Measured in Chromium:** streaming-decompressing L200.json.gz took 778 ms and produced **20 progress ticks** (about 5% each). The longest gap between chunks was 62 ms, so the page stays responsive even when this runs on the main thread.
- **What the worker sends back:** only the extracted classes, the validation result, and a slim league digest for `Pro.leagueDraft`: `{pid, tid, last ratings}` for each player, plus `teams`, `teamSeasons` and `draftPicks`.
  - **Measured:** the digest (640 KB) clones in 41 ms. Cloning the whole L50 league takes 1,683 ms, and cloning just the needed stores takes 638 ms.
- **Fallback:** `file://` blocks workers, so run the same streaming code on the main thread with an `await` per chunk.
- **Effort:** M.

### L5. Session autosave stringifies the whole league to measure it, and keeps the string
**MEASURED.**
- **Where:** `js/views.js:1180-1190` (`sessionShape`), called from `js/app.js:8270` (`saveSessionNow`) 1.5 s after load.
- **What happens:**
  - It calls `JSON.stringify(lg.data)` on the main thread just to learn the length and compare it with `SESSION_MAX_BYTES` (60 MB, `views.js:1144`).
  - L200 costs 3.1 s and L500 costs **26.7 s with a 4,266 MB renderer peak**; both are then discarded as "too big to remember".
  - A league under the cap has its string cached in the `sessionJson` WeakMap for the whole session. On L50 that took the heap from **64 MB to 169 MB (+105 MB)**, measured with CDP `Runtime.getHeapUsage` after a forced GC.
  - The 55 MB league is also written to IndexedDB; Chromium recorded 23 MB of storage use, compressed.
- **Fix:**
  - Decide from the **original byte count**, which is known at load (`File.size`, or ISIZE for a `.gz`), and never stringify a league to measure it.
  - Store the league as the **original `File`/`Blob`**. IndexedDB stores Blobs natively, with no stringify on the main thread, and the `.gz` is 6–7x smaller.
  - Do not keep the JSON strings in the WeakMap after a successful write.
  - Store the class files, which are small, as they are now.
- **Effort:** S.

### L6. Merge writes a whole string and an uncompressed `.json`
**MEASURED.**
- **Where:** `js/app.js:11748-11777` (`mergeInto`: `download(…, JSON.stringify(out.file))`), `:10224` (`download`), `:12636-12659` (league file chosen from disk).
- **What happens:**
  - Dropping an 8.8 MB `.gz` downloads a **54.7 MB `.json`**; a 28.6 MB `.gz` downloads a **213 MB `.json`**. The user has to move that around and upload it back into BBGM.
  - Renderer peak during the L200 merge: **1,976 MB** (the whole-file string plus the Blob copy, on top of the retained league).
  - The stringify and download sit outside the `try` at `:11756-11762`. A RangeError there leaves the status reading "Merging into …". The global handler (`:12437`) shows the raw "Invalid string length".
- **Fix:**
  - **Splice-merge** (prototype verified): write `{`, then for each top-level key in the original order either copy the raw bytes from the re-streamed file, or write the new `players` one player at a time (plus `bbgmdraft` and `version`).
  - Stream the output through `new CompressionStream("gzip")` into `new Response(…).blob()`. In Chromium this produced 27.3 MB from 213 MB in 6.96 s. Chromium spills large Blobs to disk.
  - Name the output `.json.gz` when the input was `.gz`. BBGM's "Create New League → upload" takes `.gz`.
  - Show progress the same way as L4.
- **Effort:** M (shares the scanner with L3).

### L7. The CLI cannot merge a league above about 245 MB, and writes it 2.19x larger
**VERIFIED.**
- **Where:** `bin/bbgmdraft.js:362-365` (`bodyOf`: `"﻿" + JSON.stringify(out, null, 2)`), `:386-395`, `:467-470`.
- **What happens:**
  - A `--merge` output is pretty-printed, which makes it 2.19x the compact size (54.7 MB → 119.5 MB on L50). Any league whose compact JSON is over about **245 MB** therefore fails.
  - Measured on L500: "merged into L500.json.gz: 75 prospects replaced" is printed, then `bbgmdraft: Invalid string length`, exit code 1, after 53 s, and nothing is written.
  - The merge output also carries a BOM, while the page deliberately omits it ("No BOM here … read back by BBGM's own league loader", `app.js:11765`). **UNVERIFIED** whether BBGM's importer accepts a BOM; the two paths should agree either way.
  - A `.gz` input produces a `_merged.json` unless `--gzip` is passed.
- **Fix:** compact JSON and no BOM for `--merge`. Write through `zlib.createGzip()` and `fs.createWriteStream` one store or player at a time, using the same splice as L6. Default to `.gz` when the input was `.gz`.
- **Effort:** S.

### L8. One damaged retired player rejects the whole league
**VERIFIED** (`s3/odd.js`).
- **Where:** `js/engine.js:665-726` (`validateLeagueFile`: the `bad[]` list applies to every row, and the age check was relaxed for leagues but this list was not).
- **What happens:**

The per-class `validateLeagueFile(cls)` at `app.js:4454` already applies the strict check where it matters.

## 4. Settings, solvers, stats, formulas and calculations

**Bottom line.** The rating side is accurate. `BBGM.ovr` matches BBGM's published coefficients and fudge curve. The solver lands on the target overall every time, with no bias (preserve mode: 360/360 exact, unrounded residual +0.004). The advanced-stat block is a faithful port of BBGM's `advStats`. The one large realism fault is in the **game-outcome model**. A convex "top stretch" in `gameStrength` (js/teams.js:1591-1607) makes the best team in the country about **1.5x too far ahead** of the field. As a result the default engine produces an **unbeaten national champion in 15% of seasons (6 of 40)**, where real Division I has had none since 1976. It also gives about 3x the real number of teams that finish with one loss or fewer, and champions averaging **2.75 losses against a real ~5**. Lowering two constants (`TOP_STRETCH` 0.7 to 0.2, `ELITE_STRETCH` 1.0 to 0.6) brings every measured record figure into the real range and still passes all 362 rows of `tools/validate.js 8`. Most settings do something. The one that partly does nothing is `injuryRate`: everything above about 1.8 is flat, and 2.0 already injures 95% of a class. The prospect-ranking layer also has a cohort-mixing flaw in its "No. N at position" label.

Evidence tags: MEASURED = I ran it (scripts in `scratchpad/s4/`). VERIFIED = I read the code and confirmed the logic. UNVERIFIED = needs a check against the upstream source or real data.

**Root cause (MEASURED with `scratchpad/s4/diag.js`, 8 seeds).** The raw team-rating spread is already realistic:

- #1 is about 63.1, #25 about 49.7, #64 about 42.7 and the mean about 30.3.
- At 0.72 points of margin per rating point, #1 vs #25 is 9.6 points per game and #1 vs #64 is 14.7. The real figures, from KenPom AdjEM converted at ~68 possessions, are about 9 and about 13.6.
- `gameStrength()` then adds `TOP_STRETCH 0.7 × (r − 50)` to every game. The effective margins become:
  - **#1 vs average: 30.3 points** (real ~21-24)
  - **#1 vs #25: 16.2 points** (real ~9)
- In the postseason, `ELITE_STRETCH 1.0 × (r − 56)` adds about 5 more points against any opponent above 50. That is exactly where an unbeaten team's last six games are played. It explains why **every unbeaten final record in the baseline belonged to the national champion**.

The noise is not the problem. `MARGIN_SD 9.4 × REGULAR_NOISE 1.2` = 11.3 points, which is right for D-I. Home edge (2.1-4.5, mean ~3.2) and momentum (`ARC_SD 2.6`) are also reasonable: momentum off moves things only modestly, and `upsetFactor` 0 barely matters because the regular season already decides the records.

- **Files:**
  - js/teams.js:1591 `const TOP_STRETCH = 0.7`
  - js/teams.js:1601-1602 `ELITE_KNEE = 56`, `ELITE_STRETCH = 1.0`
  - js/teams.js:1603-1607 `gameStrength`
  - js/teams.js:1714-1717 (the margin is `edge * 0.72 + N(0, 9.4 × 1.2)`)
- **Fix (MEASURED).** Set `TOP_STRETCH = 0.2` and `ELITE_STRETCH = 0.6`, and leave the knees, noise, home edge and momentum alone. With that change:
  - The ≤1-loss, ≤3-loss, unbeaten and champion-loss figures all land in the real band (table column 4).
  - `node tools/validate.js 8` on the patched copy: **all 362 checks pass**, the same 11 rows with no margin as the baseline.
  - 1 seeds still win 38-75% of titles across eras (band 0.15-1), 1v16 stays at 0.94-0.97, and the BPM max and plus/minus max fall slightly, away from their ceilings.
  - The 0.35/0.5 variant failed one row ("2 seed beats 15 seed" 0.72 vs a floor of 0.77 at 8 seeds). That is why 0.2/0.6 is the recommendation.
- **Guard.** Add record-distribution bands to `tools/validate.js`. Nothing bands this today: grep finds no "unbeaten" or "≤N losses" row, which is how the drift went unseen. Proposed bands per season over 20+ seeds:
  - unbeaten final ≤ 0.05
  - ≤1 loss ≤ 0.25
  - ≤3 losses 0.5-2
  - champion mean losses 3.5-6.5

### C2. `injuryRate` saturates: the top third of the slider does nothing, and 2.0 is unrealistic (MEASURED)

At js/engine.js:3132-3133, the chance a player misses games is `0.54·rate·(0.6+0.4·build)` and the chance it is an injury is `min(0.95, 0.55·rate·build)`. Both pass 1 (or the cap) at about rate 1.75-1.85. Measured over 3 classes of 60 (180 players):

| `injuryRate` | 0 | 0.5 | 1 | 2 | 3 |
|---|---|---|---|---|---|
| Players injured | 0 | 14 | 44 | 136 | 137 |

The settings sweep shows the same thing: `injuryRate` 0 and 3 both shifted output by the same small amount.

The "injury year" flavor bends this setting to 1.7 (js/engine.js:1284), which already means about 92% of a class misses games.

- **Fix.** Make the rate a hazard multiplier rather than a probability multiplier: `pMiss = 1 − (1 − 0.54·(0.6+0.4·build))^rate` and `pHurt = 1 − (1 − 0.55·build)^rate`, each capped at 0.95. That is monotone across the whole 0-3 range and identical at 1.

### C3. Settings sweep: everything else responds or is inert by design (MEASURED)

**Harness.** `scratchpad/s4/sweep.js`. Every key in `Config.CLAMP` was set to its slider minimum and maximum, plus the boolean and choice keys, on one 48-player class. Each run was compared with the default on hashes of the ratings, the stats, the team W-L, the awards and the notes.

- **No-ops on a single class, by design.** These are fine, but the panel should say "universe only" or "needs a reroll history" where it doesn't already:
  - `coachTurnover`, `realignmentMemory`, `portalRate`, `recruitMomentum`, `extrapolateYears` are universe-only.
  - `poolMemory`, `flavorMemory` and `anomalyMemory` need the `recent*` rings.
  - `flavorReach` only matters when the user has changed the settings a flavor would bend.
  - `pDII` only matters for blank colleges in "blanks" mode.
  - `lockHeights` only matters with `varySize` or a size anomaly.
  - `seasonEvents` and `draftEvents` only change news and draft-day fields.
- **Curve-only keys.** `classQuality`, `classDepth`, `eliteCount` and `rookieOvrCap` are inert under the default `ovrMode: "preserve"`. The UI does gate them (`CURVE_KEYS`, js/app.js:2355). VERIFIED.
- **Equivalent endpoints.** `archetypePool` 0 and 385 produce byte-identical results (0 = pool off = every build), and so do `rookieSkillCap`/`rookiePhysCap` 0 and 99. These match their comments but are redundant endpoints.
- **Responding as intended:**
  - `potBias` −3 / +3 moves the mean pot −5.4 / +6.3 (the comment says −4.7 / +7).
  - `pace` 58 / 82 gives 12.5 / 16.8 PPG.
  - `efficiencyEnv` and `scoringEnv` move PPG in both directions.
  - `potModel: "bbgm"` raises mean pot from 46.1 to 53.5.
  - The award strictness dials move only the awards.
- **Cross-talk (minor, MEASURED).** `pace` 58/82 also moves the class's mean pot slightly (46.06 to 46.02/46.04). This most likely comes through the production-dependent pot factors. It is harmless but undocumented.
- **Team records ignore build settings.** `specialization`, the rookie caps and `statNoise` leave team W-L byte-identical (hT unchanged), because team strength reads only `prospectTalent(ovr, pot)` (js/teams.js:17). This is a design choice: a class of specialists and a class of generalists at the same ovr win the same games.

### C7. NET adjusted efficiency uses a different home edge from the game model (VERIFIED)

`computeAdjEff` (js/rankings.js:112-113) uses `HOME_EDGE = 1.4` and `MARGIN_CAP = 10`. The game model's home edge is 2.1-4.5, mean about 3.2 (js/teams.js:1658-1661). So teams with more home games, which means the blue bloods buying games, are under-adjusted by about 1.8 points per extra home game. Real NET has dropped the capped margin, though it is not wrong to keep one as the "results" half.

- **Fix:** set `HOME_EDGE` to the mean of `homeEdge()` (3.2), or subtract each game's actual home edge, which the log can carry.

### C8. `winProb` is exported and inconsistent with the real game model (VERIFIED)

`winProb` (js/teams.js:1469-1472) is a logistic with a scale of 7.5 rating points and no stretch. The live model is a probit with a sd of about 15.7 rating points (11.3 / 0.72) plus the stretch. Nothing calls `winProb` (grep finds only the export at js/teams.js:2895).

- **Fix:** delete it, or rewrite it as `Φ((gs(a) − gs(b) + home)·0.72 / 11.28)` so any future caller (odds, previews, news) quotes the same odds the sim uses.

### C9. Prospect stars and "best at his position" (MEASURED)

- **How stars are computed** (js/engine.js:2773-2830):
  - A noised score (board order × 1.6, plus a commit-prestige pull of (55 − prestige) × 1.6, plus N(0, 12)) goes through a convex curve.
  - It is ranked within each high-school cohort (`rankCohort`).
  - Stars are then 5 for ranks ≤10, 4 for ≤40, 3 for ≤150, and 2 otherwise. Non-D-I origins are floored at rank 250.
  - Correlation of recruiting rank with final board rank is 0.47.
  - The board itself (`stockScore`, js/engine.js:4672-4712) reads no stars at all, so a 3-star who produces does rise. Board top-10s held 26% 5-stars, 41% 4-stars, 15% 3-stars and 6% 2-stars (10 classes).
- **Bug: "No. N <position>" mixes recruiting cohorts.** `posGroups` (js/engine.js:2936-2946) sorts every NCAA player in the file by `recruiting.rank`. That rank is cohort-local, so a 2026 senior's "No. 3" and a 2029 freshman's "No. 3" are compared as if they were on one list. In 71 of 89 position groups the top three spanned more than one high-school class. The note line and player page (js/engine.js:6240, js/views.js:7839) then print "No. 1 point guard" with no cohort.
  - **Fix:** group by `(hsClass, posLabel)` and print "No. 1 point guard in the 2027 class".
- **The best player at a position is barely recognised if he was a 3-4 star.** Across 10 classes there were 89 position groups.
  - In 62 of them, the class's best player at the position by ovr was a 4-star or lower.
  - Only **27 of those 62** carried "No. 1 <position>", because the label ranks recruiting score, not ability.
  - Only **13** won their positional trophy (Cousy/West/Erving/Duncan/Kareem; most go to synthetic field players).
  - Only **12** made an All-American team.
  - There is no "top-ranked prospect at his position" tag anywhere on the board or the note. The views.js "best at position…" compare selector (js/views.js:9009) is a manual tool, not a label.
  - **Fix:** add a board-derived positional rank, with the label "No. 1 PG on the board (a 3-star)". Rank by `boardRank` within `newPos` group. Add a news hook for the "under-recruited, now the best at his position" story whenever `stars ≤ 4 && boardPosRank === 1`.

### C10. Smaller formula notes

## 5. Replayability

**Method.** I generated 100 classes with the real engine in Node, loaded through `js/manifest.js` (scripts in `scratchpad/s5/`: `gen.js`, `analyze.js`, `extra.js`, `chal.js`, `mut.js`). There were three batches:

- **mem**: 50 consecutive rerolls of the 70-man sample class `Sample.makeClass("s1")`, default settings (`ovrMode: "preserve"`). The app's reroll memory was replayed between runs: `recentPools`, `recentAnomalies` and `recentFlavors` fed exactly as `rememberPool` does at `js/app.js:5371`.
- **f2**: 25 rerolls of a different sample file (`"s2"`), also with memory.
- **curve**: 25 rerolls of `s1` with `ovrMode: "curve"`.

A memory-off batch was started and killed because the machine was overloaded, so the size of the pool-memory effect is not measured on its own.

### Bottom line

What varies between rerolls is the texture: builds, flavors, anomalies and traits. What a player remembers and plays against barely moves: the class's strength, which program wins, and who goes first overall. Most of that convergence comes from the file. Several replay systems, some mutators and some flavors are partly or wholly no-ops in the default mode.

| Measure (50 rerolls, `s1`, defaults) | Result |
|---|---|
| Best overall / mean of the top-10 overall | **54 / 50.1 in every one of 50 runs (sd 0)**. In curve mode the sd is 3.3 / 1.15. |
| National champion | **Minnesota 28/50 (56%)**, Final Four 41/50. 14 distinct champions, 2.4 bits of entropy. In curve mode Minnesota is still 13/25. |
| No. 1 pick | **4 distinct men in 50.** Darius Osei 25, Tyler Hendricks 16. 41/50 come from Minnesota. |
| Distinct (champion, No. 1 pick) pairs | 19/50 |

### R1. In the default mode, class strength never changes, so many replay knobs do nothing

**Problem.** With `ovrMode: "preserve"` (the default, `js/config.js:9`), `classQuality`, `classDepth` and `eliteCount` are read only by `RB.classCurve` (`js/ratings.js:3644`). That is called only when `cfg.ovrMode === "curve"` (`js/engine.js:1743`). Three groups of features advertise those settings anyway:

- **Mutators.** "Loaded class" and "Down year" (`js/replaymeta.js:98-101`) patch only those three keys.
- **Flavors.** "Top-heavy, with a cliff" and "a two-man class" (`js/ratings.js:2085-2090`) bend nothing else. "A weak year", "one man and forty others", "weak top, deep middle", "deep talent", "top-heavy talent" and "walk-on year" bend them plus only `potSpread`/`buildNoise`. That is about 10 of 66 flavors, roughly 15% of the draw weight.
- **Puzzle.** `classQuality` is a puzzle dial (`js/replay.js:207`), and 37% of puzzles hide it (measured over 500 puzzle ids).

**Evidence.**
- Same seed, with no mutator, with "Loaded", and with "Down year": identical top-five overall, identical top-five potential, the same No. 1 pick (`mut.out`).
- Across 75 preserve-mode rerolls, the best overall and the top-10 mean have sd 0 on both files.
- "A two-man class" and "one man and forty others" printed the same 54 / 50.1 curve as "balanced".

**Proposal.**
- (a) Have "Loaded class" and "Down year" also set `ovrMode: "curve"`, which is a one-line patch each. Or move their effect onto `potBias`/`potSpread`, which are live in preserve mode.
- (b) In preserve mode, map a flavor's `c.classQuality`/`eliteCount` onto potential: elite slots get a pot ceiling, and a weak year gets a negative `potBias`. Otherwise label the flavor honestly, e.g. "(strength from file)" in the class name at `js/app.js:4251`.
- (c) Drop `classQuality` from `PUZZLE_DIALS`, or start puzzles in curve mode.

**Effort.** S.

### R2. A fixed file decides the champion and the No. 1 pick

**Problem.** A prospect's school comes from the file (the default college source). In preserve mode his overall is also the file's. So whichever program the file hands its two best prospects becomes a near-permanent favourite. In `s1`, Minnesota has the No. 1 and No. 3 prospects plus two more.

**Evidence.**
- Minnesota won 28/50 titles and reached 41/50 Final Fours, and was the final No. 1 in the poll 27/50.
- Only 4 distinct No. 1 picks appeared in 50 runs. Curve mode does not fix it (Minnesota 13/25).
- On `s2` the anchor was weaker: Wake Forest was school of the No. 1 pick 12/25 times, and champions spread to 4.0 bits.

**Proposal.**
- Add a **reroll scope** next to Reroll: *season only* / *players* / *schools too*. "Schools too" redraws file-assigned colleges with the existing talent coupling (`Engine.destinationPool`, `talentTerm`).
- Add a "Transfer frenzy" mutator that sets the college source to redraw.
- Show a one-line "file gravity" warning when one program holds two or more of the file's top five.

This is the cheapest way to make the champion and the No. 1 pick differ between rerolls.

**Effort.** M.

### R3. Play mode: answers can be memorised, the record can be farmed, and the tab title leaks the season

**Problem.**
1. A reroll always lands on the results tabs. A game can only start after the class has rendered (`js/play.js:273-316`), and the play state resets on every reroll (`play.js:277`). There is no way to play a class "cold", so after one or two rerolls of a file the answers are known.
2. `saveRecord` (`play.js:219`) does not dedupe by seed or file. Start, reveal, press Done and start again on the same seed: each pass adds to the totals and can replace "best".
3. `document.title = className(res)` (`js/app.js:5818`) includes the first storyline ("chalk all the way", "a wide-open year"). That shows in the browser tab while the other tabs are gated.

**Evidence.** Fixed picks with no information (Minnesota, Darius Osei, Darius Osei) score **6.02/11 on average** over 50 rerolls. The champion pick alone averages 3.3 of a possible 5.

**Proposal.**
- Add a **"Blind reroll"** (play-first) button. It rerolls with `st.play` pre-opened, so gating applies before the first render.
- Record only the first reveal per `seed + fingerprint`.
- Score against a baseline, the way Blind scout already does with `preseasonTop10`. For prediction the baseline is "prestige favourite + preseason No. 1"; report points above it.
- Mask the narrative in the title while a game is open.
- Add streaks to `loadRecord`: N games above baseline in a row.

**Effort.** S–M.

### R4. Mutators bypass the challenge budget

**Problem.**
- `effectiveCfg` applies `state.mutators` after clearing the class memory for challenges (`js/app.js:5338-5344`).
- `scoreChallenge` counts moved dials by diffing `state.cfg` (`app.js:6627-6630`), and `state.cfg` never contains mutator patches.
- `startChallenge` (`app.js:6713`) does not clear mutators.

So "Chaos March" gives `upsetFactor: 2` and "One-and-done" gives `freshmanShare: 75`, with **0 dials counted**. Those are exactly the published levers for the Cinderella and daily goals (`js/replay.js:20-26`). Par scores (`parScore`) and rival codes become meaningless.

**Proposal.** Either clear and forbid mutators while a challenge is active, or count each mutator's patch keys as moved: diff `effectiveCfg()` minus the memory keys instead of `state.cfg`.

**Effort.** S.

### R5. "Fixed for everybody" challenges are fixed per file, not per person

**Problem.**
- The daily blurb says "Today's class, fixed for everybody" (`js/replay.js:56`). But a challenge is only a seed plus settings, run over whatever file is loaded (`startChallenge`, `app.js:6713-6720`).
- `resultCode` and `replayLinkFor` drop `fp` (`app.js:2707`, and the `delete payload.fp` near the `resultCode` function), so a rival's code from a different file compares unrelated classes.

**Evidence.**
- The goal "No. 1 pick is a freshman" holds in 92% of `s2` rerolls but only 18% of `s1` rerolls.
- Mean strangeness is 16 on `s2` and 34 on `s1`, where two bingo squares are always free.
- So the same daily is trivial for one player and near-impossible for another.

**Proposal.**
- Run daily, campaign and puzzle on a **canonical synthetic class**, `Sample.makeClass("daily-"+date, 70, year)`. The Universe mode already does this with `synthFile` (`js/universe.js:3517`).
- Put the fingerprint in result codes and show "rival played a different class" on a mismatch.
- Keep "challenge on my own file" as an explicit option.

**Effort.** S–M.

### R6. The daily's vocabulary is tiny, and its solutions are published

**Problem.**
- The daily draws from 3 common and 4 stretch goals (`js/replay.js:19-26`), and each stretch goal ships a one-dial `lever`.
- Over 365 days there are 36 ordered goal tuples, about 22 sets. A given stretch goal recurs every ~4 days, so the solution is learned within a week.
- The tall-prospect goal depends on file heights: `lockHeights` is on by default (`config.js`), so its lever `specialization` cannot move heights. It only reshuffles the board order.
- The share line lists the exact changes (`challengeResultText`, `app.js:6773-6777`), so pasting a result spoils the day.

**Proposal.**
- Draw goals from every predicate plus the parametric clauses (`topOvr:N`, `archetype:X`, `school:X`, `pos1:X`, `freshmen:N`, at `js/engine.js:4867`), including `!` negations, banded by measured hit rate on the canonical class.
- Add a weekly theme.
- Make the shared text spoiler-free, Wordle-style: goals as ✓/·, dial count and run count, no dial names.
- Add a daily streak counter in `BEST_KEY` storage.

**Effort.** M.

### R7. Puzzle dials are part lottery, part no-op

**Problem.** `PUZZLE_DIALS` (`js/replay.js:202-210`) includes:
- `variation`, which by its own documentation is a pure per-player RNG salt (`config.js:114-122`). Finding it is a 1-in-4 guess, which contradicts the puzzle's premise that "rerolling is not the answer".
- `classQuality`, a no-op (R1).

Together they make up roughly 2 of every 7 hidden dials. Nothing checks that a puzzle's target is uniquely reachable.

**Proposal.**
- Replace both with dials whose effects show in the four headlines: `injuryRate`, `pace`/`scoringEnv`, `bluebloodDownYears`, `coachTurnover`.
- At generation, reject a puzzle if the defaults already reproduce two or more headlines.
- Add a hint economy: reveal which fieldset a hidden dial lives in for −10 points.

**Effort.** S.

### R8. Narratives are drawn before the season and never checked against what happened

**Problem.**
- `applyNarrative` (`js/engine.js:1360-1395`) draws 2–3 storylines before the season, bends settings, and then states them as fact, both in the class name and as "The season: …" (`js/views.js:2631`).
- There is no memory: unlike flavors there is no `recentNarratives`.
- Contradictory pairs are allowed: "a wide-open year" with "chalk all the way", or "a scoring explosion" with "a defensive slog".

**Evidence.** Across all 100 runs:
- "The mid-majors run" → mid-major champion **0/23**.
- "A dominant favourite" → the final poll No. 1 won the title as a 1 seed only 6/21.
- "A wide-open year" → champion seeded 3 or worse, or a double-digit Final Four team, 6/27.
- Contradictory pairs in 4–6% of classes.

**Proposal.**
- Keep the bends as a *preseason* storyline. After the simulation, relabel from outcomes: "the mid-majors were supposed to run" versus "the mid-majors ran".
- Ban contradictory pairs.
- Add a `recentNarratives` memory alongside the existing flavor memory (`js/ratings.js:2890`).
- Verified narratives also make a good hidden-information prediction market: "will this storyline come true?"

**Effort.** S–M.

### R9. Bingo and achievement rarity is uncalibrated and depends on the file

**Problem and evidence.**
- Squares tied to absolute overall cut-offs (`js/replaymeta.js:26-27`) are always or never hit on a given file. On `s1`, "Nobody reaches 55" hit 50/50 and "6'1" in the top five" 47/50. "Six at 55+" hit 0/100, as did "Stacked" (8 at 55+). These cannot fire in preserve mode with typical BBGM files, whose top prospects sit around 50–56.
- Strange-70, Anomalous and Out of nowhere fired 0/100.
- "Perfect season" (unbeaten champion) fired **9/50**, so the `bloodlines` unlock (`replaymeta.js:216-221`) is trivial. "Undefeated November to March" fired 18/50 on `s1`, which is unrealistic and a symptom of R2's dominance.

**Proposal.**
- Define squares relative to the file: top prospect above the file's 90th percentile, or potential-based thresholds.
- Add a measured rarity table to `tools/tests`, the way the daily bands are already measured.
- Tier achievements bronze/silver/gold by measured rate.
- Gate unlocks on rarer feats.

**Effort.** S.

### R10. Repeated text is what makes rerolls feel the same

**Evidence (mem batch).**
- 62 season-event templates for 292 events. "…needed eleven minutes of review and four ejections…", "Two technical fouls in the last minute decided…" and "largest home crowd in the programme's history" each appeared 11 times in 50 classes (`js/teams.js:2200-2400`).
- 69% of note first lines begin "A <height> <class>"; 100% of scouting paragraphs begin "Scouts note".
- Draft-night events are 9 kinds, about 5 per class, so every class shows more than half of them.

**Proposal.**
- Add a phrase memory like the anomaly memory: `recentTemplates` from the last 3 classes, used as a down-weight in `rng.pick`.
- Rotate the note opener (stat-led, story-led, origin-led).
- Give "Scouts note" 6–8 attributions; `news.js` already has an attribution system.
- Double the draft-event table.

**Effort.** S–M.

### R11. The build pool varies but has no identity and nothing to collect

**Problem.** Consecutive pools share about 5% of their builds; 384 of 385 builds appear within 50 classes, and the top-ten slots used 240 different names. Variety is high, but nothing persists and nothing rewards noticing a rare build. "Balanced" is still the most common top-ten build (44 of 500).

**Proposal.**
- Add a **build collection ledger**, the same storage as the achievement ledger (`app.js:2626-2651`). It would track builds seen in a top-ten, the first seed for each, rarity tiers from `RB` weights, and completion achievements.
- Highlight a "build of the year" in the class name when the pool's rarest build reaches the lottery.

**Effort.** S.

### R12. Missing replay loops, built on existing hooks

1. **Draft-night GM game.** You hold pick N in the mock draft (`Pro.mockDraft`, `js/pro.js:448`). Ratings are fuzzed (`Engine.scoutingFuzz`, `js/engine.js:7347`); the CLI already has `--scouting`. You pick, and the grade comes from `Pro.project`'s median peak against the man taken at the same slot. Seeded, so it is shareable as a code. This is the biggest missing loop. **Effort:** M.
2. **Scenario packs.** Challenge tables as JSON imported through `Replay.encodeCode`/`decodeCode` (`js/replay.js:157-172`), with the canonical class from R5. Community-made campaigns would need no new engine work. **Effort:** S–M.
3. **Rivalry and follow goals for a single class.** `followedLead` and `rivalryTable` exist only in Universe mode (`js/universe.js:4337`). Let a single-class player pick a program before a blind reroll and score its season. **Effort:** S.
4. **Hidden-information modes.** "Fog" hides overall/potential on the board and uses the Blind column preset; "storyline market" is R8; "upset factor hidden" shows bracket difficulty only after the reveal. **Effort:** S.
5. **Weekly ladder.** The daily's par scores summed Monday to Sunday into one shareable code. Pure, since `Replay.dateKey` and `parScore` already exist. **Effort:** S.

## 7. Universe mode

**Bottom line.** The chain is solid. Across 46 played seasons there were no failures, no thrown seasons and no console errors in the browser, and a world you replay or extend comes out the same. The problems are in what the world *feels* like over 20+ seasons, and in what is missing around it:

- Elite seasons are too common.
- Coaches hardly ever move between programs.
- The top of the program ladder squeezes together.
- About 1 in 9 people in the registry is the same man stored twice.
- The national player of the year is sometimes missing from the timeline.
- Every synthetic name has a "Jr."/"III" suffix.
- In the browser the whole run happens on the page's main thread, which freezes the page for 4–10 s per season.
- A BBGM league's real pro history never gets into the world.

**How I measured.** Synthetic chains driven through `Universe.beginChain` exactly the way `js/app.js` does it: seed `s7audit` for 24 seasons (2030–53) and seed `otherseed` for 22 seasons, 364 programs each, plus 12 standalone seasons as a control and an 8-season run in headless Chromium.

### UV1 — The universe run freezes the page for 4–10 s per season
- **Problem.** `runUniverse` in `js/app.js` (≈7535–7565) calls `chain.step(k)` on the main thread and yields only *between* seasons (`setTimeout(() => step(k+1), 0)`). Each season is one synchronous `runner.run(cfg)`.
- **Evidence.** In headless Chromium, an 8-season synthetic universe logged 19 long tasks; the top nine were 3.8–9.5 s. The page, the Stop button and the status line cannot respond during a season. A 40-season world is ~5 minutes of a mostly frozen tab.
- **Proposal.** Run the chain in `js/worker.js` (it already hosts the engine for batch mode). `beginChain` is pure apart from `spec.store` and `runnerFor`. Post a compact row plus program rows after each season, and keep `evictUniverseResults` semantics by asking the worker for a result on demand (`universeCfgFor` already rebuilds evicted ones). Cheaper interim fix: split `runner.run` into its phases (`phasesRun` already exists) and yield between phases, which cuts the long task to roughly one phase.
- **Effort.** M (interim fix) / L (worker).

### UV2 — The national player of the year drops off the timeline when he belongs to a later class
- **Problem.** `summarize` (`js/universe.js:936`) and `alumniOf` (`:892`) call `pickPOY(res.players, …)`. The underclassmen of later classes live in `res.futurePlayers`, and they win the trophies.
- **Evidence.** `row.poy === null` in 2030 and 2031 (seed 1) and in 2035 (seed 2). In a 4-season check, the 2031 Consensus/Naismith/Wooden winner was `Trey Brooks III` from file 2. Underclassmen from later classes take about 65 honors a season, so the timeline's POY column, the alumni index, `records.poys`, the hall of fame and the "back-to-back POY" threads all miss real winners.
- **Proposal.** Pick from `res.players.concat(res.futurePlayers || [])`, which covers both later-class underclassmen and undrafted returners (`past`). Carry `id = playerId(fp(fp.fileIndex), fp.homeKey || fp.key)` so the entry links to his own file's career. Also store `poy.classSeason`. Add a test that `row.poy` is non-null whenever any national POY trophy was minted.
- **Effort.** S.

### UV3 — Synthetic re-entrants become two people in the registry
- **Problem.** `applyEntrants` (`js/universe.js:3573`) writes a returning senior into the next synthetic class as `pid: 1000+i`. `registryOf` then mints a fresh identity `fp/100x`, while the old identity gets only an `"re-entered the draft"` season (`step()`, ≈3940).
- **Evidence.** 219 of 1,899 registry identities (11.5%) share a name with another identity, and every one of those pairs is an `/100x` id. There are zero true name collisions. One identity holds his college seasons and his undrafted draft row; the other holds the draft he was actually taken in.
- **Proposal.** Stamp `bbgmdraftId: x.id` on the entrant row. In `registryOf`, prefer `p.bbgmdraftId` over `playerId(fp, key)` (and carry it through `biographyOf`). Or keep a `u.registryAlias` map that `mergeRegistry` folds.
- **Effort.** S.

### UV4 — Every synthetic name carries "Jr." or "III"
- **Problem.** `uniqueNames` (`js/universe.js:3504`) uses the absolute season: `idx = season*stride + pid` and `generation = floor(idx/P) % 8`. With `P ≈ 2,150` pairs and `season ≈ 2030`, the generation is never 0.
- **Evidence.** `synthFile("x", 2025|2030|2031|2040|2055)` gave 70 of 70 suffixed names in every case. 1,899 of 1,899 registry names are suffixed. This also hides the real-father/son `relatives` story the export tells.
- **Proposal.** Count from a seed-derived epoch: `idx = (season - epoch(seed)) * stride + pid`, with `epoch = 2000` or the first season, clamped at ≥0. Enlarge `SYNTH_FIRST`/`SYNTH_LAST` (50×44 → about 150×150 ≈ 22k pairs, roughly 300 seasons before a wrap). Version the fingerprint, because names move every synthetic `resultFingerprint`.
- **Effort.** S.

### UV5 — Too many generational seasons
- **Problem.** Mostly engine-wide; see §4. The standalone control gives 0.33 unbeaten regular seasons per season against 0.37 in the universe. The universe adds dynasties on top: Kentucky went 41-0 twice running at level 88, and UCLA three-peated including a season at level 62.
- **Evidence.**
  - Unbeaten regular seasons are about 3× the real rate.
  - 21 of 46 seasons have a ≤1-loss team (real: about 1 in 5 years).
  - Champions average 3.0 losses (real about 5).
  - Champions average 40.7 games; every one plays 31 regular + 4 conference-tournament + 6 NCAA games, and real top seeds get conference-tournament byes.
- **Proposal.**
  1. Add a universe realism test (beside `tools/tests/universe-realism-programs.js`) on a 20-season chain with these targets: unbeaten ≤0.2/season, champion losses mean 4–6, ≤1-loss seasons ≤35%, no back-to-back perfect seasons, at most one three-peat per 25 seasons.
  2. Damp dynasties in universe-only terms. After a title, add early-entry attrition: the champion's top two returners are more likely to leave, read from `carry.titles`. Cap the recruiting-momentum boost (`Recruiting momentum` dial) by the program's title streak.
  3. Give the top two conference-tournament seeds byes.
  4. Hand the win-probability steepness to §4.
- **Effort.** M.

### UV6 — Records come apart from program level; mid-majors win titles as top seeds
- **Evidence.**
  - 15 programs ranked >100 by level had ≤3 regular-season losses: The Citadel (level rank 285, then 296) went 28-3 in both 2032 and 2033; Ohio (MAC, rank 148) went 31-0.
  - Bradley, at level rank 108, won the 2047 title as a **No. 1 seed** after realignment had moved it into the Big East.
  - 4 of 24 champions were programs ranked >100 (Temple, Ohio, Bradley, Duquesne). Real: about 0 since 1990.
- **Proposal.**
  - Seeding: put strength of schedule in the seed and selection score; a 28-3 Southern Conference team should be a 9–12 seed.
  - Realignment: before a league admits a school, gate on its level against the league median; the conference-membership rules in `js/teams.js` are the place.
  - Add test assertions on champion level rank (p90 ≤ 40) and on 1-seeds' level rank (≤ 30).
- **Effort.** M.

### UV7 — The coaching carousel almost never moves a sitting coach
- **Problem.** `coachingCarousel` (`js/teams.js:2785`) draws "hired away" with probability 0.006–0.30, mostly only after a deep March run. `carouselMoves` (`js/universe.js:505`) only moves a man into a vacancy that opened *that April* at a higher-prestige program. Fired men vanish.
- **Evidence.** 84 hired-away departures in 24 seasons, but only 56 program rows carry `movedFrom` (2.3 a season). Just 6.6% of coaches ever led two programs. In real Division I, roughly half of all hires are sitting head coaches, and fired coaches are often re-hired a level down.
- **Proposal.** Fill vacancies as a ladder:
  1. Rank the open jobs by prestige.
  2. Fill each from the best-performing sitting coach at a lower-prestige program, judged on a two-season win rate against expectation.
  3. His old job becomes a vacancy and is filled the same way.
  4. A first-year stranger fills only what is left.
  5. Keep fired and NBA-returning men in `carry.coachPool` for three seasons as retread candidates for lower jobs.

  The coaching tree (`coachTreeStep`, `js/universe.js:799`) then gets real branches. Add a test: lateral moves ≥15 a season at `coachTurnover` 100.
- **Effort.** M.

### UV8 — The top of the program ladder flattens over decades
- **Evidence.** The 25th-best program falls from 74.4 to 69.6 (seed 1) and from 75.5 to 69.1 (seed 2). The 10th-best falls from 79.1 to 75.3 and from 79.0 to 72.5. The mean stays around 46–51, which is the only thing `uv11/league mean level stays near the middle` checks.
- **Proposal.** Make the regression in `carriedLevel` (`js/teams.js:92`) and `ageCarry` (`js/universe.js:685`) preserve quantiles. Pull each program toward its *rank's* level in the season-one distribution, not toward the mean. Or re-standardize the level distribution to the initial p50/p90/p96 every season. Add `uv11` assertions that p90 and p96 stay within ±3 over 24 seasons.
- **Effort.** S–M.

### UV9 — What gets kept, and how honors are counted
- **Problem 1.** `registryForStorage` (`js/app.js:~330`) keeps the 300 longest *spans* (span ≥2). One-and-done No. 1 picks and players of the year have span 1, so after a localStorage-only reload (an IndexedDB failure or quota shed) the Careers table, `proHall` and `peopleRecords` lose exactly the stars.
- **Problem 2.** The registry's honors include watch lists, honorable mentions, All-Region, All-Tournament and All-Freshman teams: 2,549 of 6,630 entries (38%). `proHall` and the hall score count every one the same (`personalHonors(x).length * 2`).
- **Proposal.** Keep registry entries by a score (national honors, draft slot ≤ 14, span), not by span alone. Weight honors by tier: national trophy 5, All-America 3, conference player of the year 2, all-conference 1, lists 0.
- **Effort.** S.

### UV10 — Memory and storage growth
- **Evidence.**
  - `u.cfgs[i]` keeps a full `carryOver` copy (≈200 KB) for every season: 6.3 MB at 24 seasons and 8 MB at 30, never bounded, even though "memory is bounded" applies only to results.
  - `u.links` holds live future-player objects; it is circular (`JSON.stringify` throws) and keeps result graphs alive. In the Node run the heap climbed 61 → 409 MB before a full GC.
  - In IndexedDB, programs (57 KB/season) and registry (46 KB/season) dominate: about 10 MB at 100 seasons. `universeFull()` deep-clones everything through JSON on every autosave: 420 ms at 30 seasons, on the main thread.
- **Proposal.**
  - Keep `carryOver` only every K = 5 seasons plus the last one; resume from the nearest checkpoint and replay forward, which costs at most 4 seasons.
  - Store `links` as `{fileIndex, key, season}` and rebuild the rest from the result.
  - Store program rows as columns per program, e.g. `{seasons:[…], level:[…], w:[…], …}`, which is about 3× smaller.
  - Autosave with `structuredClone` or by handing the object straight to IndexedDB (it clones itself) instead of a JSON round-trip, and write only what changed (`rows`, `programs` for the newest season).
- **Effort.** M.

### UV11 — History pages: no "drafted from" view, an invented pro career, no prehistory
- **Problems.**
  - A program's page (`programHistoryBlock`, `js/views.js:4611`) shows level, coach, record and March results, but **no players**. Nothing lists who the program sent to the draft, even though the registry has `draft.school` for every man.
  - The pro career is a seeded invention (`proOutcome`, `js/universe.js:4406`).
  - The world has no banners before season one, so threads say "first title of this timeline" about Duke and the digest's "first title in N years" cannot fire before season N.
- **Proposal.**
  - Add `Universe.programAlumni(u, name)`: registry entries grouped by `draft.school`, plus underclassman seasons by `school`. Render an **"Alumni / drafted from"** table on the program page and a Universe-tab view of it filtered by draft year. Columns: name, years, class year, draft season and slot, honors, pro line.
  - Mark `proOutcome` as "projected" and replace it with real data when UV12 supplies it.
  - Optionally seed `carry.titles` and `carry.digest` from a small real-history table (title counts and last-title years) behind a setting.
- **Effort.** M.

### UV12 — Pull the last 4 drafted pro classes from a BBGM league export into the universe

Every player whose `draft.year` is in the last four seasons gets a college program, back-filled college seasons, stats, awards and notes, and shows up in the alumni lists, the "drafted from" pages, the hall and the registry. His real pro career is attached.

**Hooks that exist today:**

**Design, in three tiers:**

1. **Detection.** Add `Engine.pastClassesIn(league, {back: 4})` beside `draftClassesIn`.
   - Years: `S-4 … S-1`, plus `S` when `gameAttributes.phase ≥ 5` (that season's draft has happened). `S` comes from `findSeason`.
   - Players: any `tid` (on a team, `-1` free agent, `-3` retired, undrafted with `draft.round 0`).
   - Return `{year, drafted, undrafted, ours}`, where `ours` means `tid -7` rows or `bbgmdraft.pot[year]` are present.

2. **Ledger import, no re-simulation.** This tier works on a universe that already exists. Add `Universe.importProHistory(u, league, opts)`.

   - Honors: awards with `season ≤ draft.year`.
   - Pro career: `pro: {real: true, seasons, gp, ppg, team, status, awards after draft}`, summed from stats rows with `tid ≥ 0` and `playoffs: false`.

   - `proOutcome` returns `entry.pro` when it is real.
   - `registryForStorage` must keep `pro.real` entries (see UV9; they have span 1).
   - Cost: milliseconds; it does not touch seeds or fingerprints.

3. **Retroactive seasons.** The four years become played seasons. Add `Engine.extractPastClass(league, year)`, which rewinds each man to draft night:
   - ratings = the newest `ratings` row with `season ≤ draft.year` (cross-check against `draft.ovr` / `draft.pot`);
   - `tid = -2`; pro `stats` stripped; `pid` and `born` kept;

   When the league carries a recipe for that year (make recipes per year, UV13), use its seed and settings: the class replays exactly, and `resultFingerprint` can verify it. Otherwise, when `tid -7` rows exist, overlay those stats and awards on the result (restore, the way `restoreImported` does for rows) so the tool's earlier export stays the truth.

   Chain placement:
   - **Cold:** `runnable` is sorted by season, so `[S-4 … S-1 pro classes] + [S…S+2 future classes from draftClassesIn]` is one continuous world. The future classes' underclassmen land on the past seasons' rosters through `rosterFor`, and the undrafted past men return through `pastRosterFrom`.
   - **Existing universe:** a class in the middle of the timeline cannot extend it (beginChain `extend`). Offer "resume from season X" (`mode: "resume"`, `from = first row with season ≥ S-4`) or fall back to tier 2.
   - Flag these files `pastPro: true`. `exportPlayersFile` and `mergeIntoLeague` must skip them, because these men already exist in the league with pro careers.

   **Effort.** Tier 1 S–M; tier 2 S; tier 3 M–L. Tests:
   - a synthetic league with four past classes: every drafted man gets a registry entry linked to the program, and `draftSlot` equals the real pick;
   - an imported class this tool wrote comes back with the same college rows;
   - a re-import is idempotent (same `lg:` ids, no duplicate alumni).

### UV13 — A merged league remembers only one recipe
- **Problem.** `file.bbgmdraft.recipe` is a single object (`js/engine.js:8203`, `:9182`). Merging a second class overwrites the first class's seed, while `pot` is already keyed by year.
- **Proposal.** Write `bbgmdraft.recipes[year]` and keep reading `recipe` for compatibility. This is what lets UV12 tier 3 replay past classes exactly.
- **Effort.** S.

### UV14 — The file fingerprint samples only 9 players
- **Problem.** `fileFingerprint` (`js/universe.js:4484`) hashes the count, the season and the first 6 plus last 3 `pid:name` pairs. Two edited versions of one class (a middle player renamed or re-rated), or league-extracted classes that differ only in the middle, collide. The fingerprint keys the seed, identities (`playerId`) and import matching.
- **Proposal.** Hash every `pid|name|born.year|last ratings.ovr`; it is cheap. Bump `ENGINE_REV` or the export version, and accept the old fingerprint as an alias when replaying v3 files.
- **Effort.** S.

*Why:* "My team" can only highlight the team's picks and list its targets. The user never makes a pick. This is the cheapest move toward a draft game (see F1).
*Where:* pro.js `mockDraft` (361), `mockUi` and `mockFor` in views.js (6811-6843). Add `forced` to the cache key.

*Effort:* M.

## 10. Larger features and next steps

Each item below is more than a day of work. Each gives a design sketch, the code it builds on (file:line), its risks, and its dependencies. The quick wins in §9 are named where they are stepping stones. Every item was grepped to check that it does not already exist. Where something nearby exists (the Dynasty goal, the Redraft button, the seeded pro tail), the item says what it adds.

---

**F1. Draft War Room: an interactive draft with pick trades.**
*Sketch:* Turn the Mock tab from a report into a draft you take part in. It is a state machine over `{slots, picks, pool, owners}`. The computer picks with the existing `valueTo` (pro.js:195). The user controls one or more teams, and at their slot they choose from `targetsFor` (pro.js:428) or from the full pool (Q1). Trades work through a pick-value chart, which is the expected projected peak by slot from the ADP pass (Q2). A computer team on the clock offers to trade down when its best target's value is under the next team's interest by a margin. A computer team trades up when its top target is about to go and its plan is "contending" (`t.plan` in `teamsFor`/`leagueDraft`, pro.js:160/239). The user can propose a trade, which is accepted when the value received is at least the value given × (1 + a reluctance draw). The draft ends in an ordinary `mock` object, so the CSV, PNG, markdown and `proLines` exports keep working, plus team grades (Q3).
*Hooks:* pro.js `mockDraft` 361 (picks are already keyed by pick number, `"mock-pick|seed|salt|n"` at pro.js:388, so a user choice changes only the pool and not the other teams' tastes); `leagueDraft` 239 (real traded picks, `via`); views.js `viewMock` 6940, `mockExtras` 6881; the engine's draft-night events already speak of trades (news.js "trade up" rows), which can read the War Room's trades when one exists.
*Risks:* The state must live outside `proFor`'s WeakMap cache (views.js:6790) and survive re-renders and undo, so store it on the file the way locks are. In league mode, traded *future* picks would need `draftPicks` for later seasons. Mobile layout: the mock table is already wide.
*Depends on:* Q1, Q2, Q3. *Size:* 4-6 days.

**F2. Merge the drafted class into the league ("draft it for me").**
*Sketch:* An option on *Merge into a league file* that applies a finished mock or War Room draft to the league. For each pick it sets `tid`, writes `draft = {round, pick, tid, originalTid, year}`, gives a rookie contract from the league's `gameAttributes` (rookie scale, `draftPickAutoContract`), removes the consumed `draftPicks` rows, and sends undrafted men to free agency (`tid = -1`). The result is a league that can be loaded straight into the regular season with the tool's draft already made.
*Hooks:* engine.js `mergeIntoLeague` 8964 / `mergeManyIntoLeague` 9220; pro.js `leagueDraft` 239 (it already reads `draftPicks`, `teams` and `teamSeasons`); bbgm.js `LEAGUE_DATABASE_VERSION`; the import-path reimplementation `tools/universe.js` uses for its checks.
*Risks:* The BBGM schema moves between versions. The merge has to refuse a league not in the draft phase. The league has roster limits (15) and a hard or soft cap. Contract-amount formulas vary by league settings. Mitigation: refuse rather than guess, and state every assumption in the change report (`changeReport`, engine.js:8254).
*Depends on:* F1, or the plain mock. *Size:* 3-4 days.

**F3. The season time machine: "as of" any date, plus bracketology.**
*Sketch:* A date scrubber, from preseason to Selection Sunday, that re-reads the season as of day *d*. A pure `Season.asOf(res, d)` returns a light proxy result:
- records from the games in each `t.log` with `day <= d`;
- the poll from the matching week of `res.pollHistory` (engine.js:3383, 15 checkpoints);
- NET and quadrants from `Rankings.computeRankings` (rankings.js:211) over the truncated logs;
- each prospect's line accumulated from his `gameLog` rows up to that game;
- the paper filtered by dateline (news.js:51).

Bracketology runs `Tournament.selectField` (tournament.js:33) on the as-of teams each week and shows the projected field and seeds, "last four in" and movement. The existing "bracketology" news kind can then quote the real projection instead of only end-of-season facts.
*Hooks:* teams.js `scheduleDates` 2027 (`f.day`); `t.regSnapshot` (engine.js:3240); `pollHistory`; stats.js `gameLog` 3995; views.js `viewTeams` 3488, `conferenceStandings` 8259, `viewNews` 3857.
*Risks:* `computeRankings` iterates adjusted efficiency (up to 400 passes over 364 teams), so cache one result per poll week and snap the slider to weeks. Every view reads `res` directly, so scope the first version to Teams, Standings, Poll, News and the player page, and gate the other tabs while a date is set (the way `Play.gated` does, play.js:245). The weekly poll was drawn with its own RNG and must not be recomputed.
*Size:* 5-7 days. Bracketology is about 2 more.

**F4. A pro projection that predicts what BBGM will do with the player.**
*Sketch:* `Pro.project`'s career curve (pro.js:64-95) is a hand-written miniature of player development. The tool already reimplements BBGM's `ovr` (bbgm.js) so that export matches what the game computes. Do the same for development: reimplement BBGM's per-season, per-rating age progression (the ratings-level development step with its age curves and randomness, coaching rank at the league mean). Run the 41 careers on the full `newRatings` vector rather than on ovr alone, and take ovr through `BBGM.ovr` each season. Then the projection is "what this file will become in BBGM", and builds age differently by construction (athleticism falls first and IQ rises), which retires Q5's per-tag heuristic. Then replace `Universe.proOutcome` (universe.js:4406) with this model, seeded on the registry id (Q4), so the Hall of Fame, the hindsight redraft (Q28) and the player page all read one model.
*Hooks:* pro.js `project` 107, `oneCareer` 73; bbgm.js `ovr`, `RATING_KEYS` 25; universe.js `proOutcome` 4406, `proHall` 4429; `tools/tests/pro.js`.
*Risks:* Licence and attribution for porting game logic: check BBGM's licence before copying formulas and document provenance as the `ovr` port does. Drift when BBGM changes its model, so pin a BBGM version in a constant and test against recorded fixtures. Cost is about 41 × 15 seasons × 15 ratings per player, which is fine but should be lazy (it already is, through `proFor`).
*Size:* 4-5 days.

**F5. Coach mode: a career as a head coach in Universe mode.**
*Sketch:* The Dynasty goal (app.js:7869, universe.js:4357) currently scores how far *settings* can be nudged. Coach mode gives the user a seat instead. The user is a named coach at a program (made by `makeCoach`, teams.js:666, carried in the chain's coach state). Each off-season the user:
1. picks a style from `PROGRAM_STYLES` (drift is still applied);
2. spends a budget of scholarship offers on the next high-school cohort (Universe ranks every cohort across the chain, universe.js:3313 `recruitingCohorts`). An offer raises that program's weight for that prospect in `assignCollege` (engine.js:453), the same path `recruitMomentum` already bends, and the recruitment record (`assignRecruiting`, engine.js:2862: offers, finalists, decommits) shows the user's program in the cut;
3. after a good season, receives job offers from the carousel (`coachingCarousel`, teams.js:2785, already models "hired away"). After a bad one, the existing hot-seat model (`hotSeatPreview`, universe.js:2797) can fire the user.

Decisions are stored as data in the universe export, beside the biographies, so a shared coach career replays exactly.
*Hooks:* the above, plus universe.js `beginChain` 3611 / `step` 3849, `ageCarry` 685, `coachTreeStep` 799; app.js dynasty functions 7841-7945.
*Risks:* The chain's invariant is that the build phase depends only on the seed and the pool memory (README, "three passes"). Offers break it for exactly the prospects offered. `recruitMomentum` is already a universe-only exception, so follow its pattern and make the decisions part of the frozen config. Extending a chain past a decision is fine. Inserting one in the middle forces a rebuild, which the tool already reports for mid-timeline classes.
*Depends on:* F15 (a cohort view to recruit from). *Size:* 8-12 days.

**F6. Export a universe as a website.**

The site also has program pages (`programHistory`, universe.js:2911) and person pages from the registry (universe.js:3162). *Hooks:* site.js `data` 559, `READER` 733, `embed` 600; universe.js `exportUniverse` 2953 (v3 already carries rows, threads, records and alumni); app.js `ensureResult` 5641 to rehydrate evicted seasons.
*Risks:* Size: 40 seasons of season data. Strip each one to its summary tables and measure. Export time: every evicted season has to be re-simulated, so run it asynchronously with progress and cancel, like the chain itself. The reader script grows.
*Depends on:* Q26 (shared table renderers). *Size:* 4-6 days.

**F7. BBGM companion loop: one universe that follows a live BBGM league.**
*Sketch:* The commissioner's workflow is: export the league, make the class, import it, play a BBGM season, repeat. Companion mode recognises the league (league name, `startingSeason`, team set) when its export is dropped and:
- finds the draft classes not yet played (`classesFromFile`, app.js:4415);
- extends the chain (`canExtendUniverse` 7223, `appendFiles` 4741);
- merges the new class back (engine.js:8964, optionally drafted by F2);
- records a map from the registry id to the BBGM `pid` (`playerId`, universe.js:3075).

The next export then carries *real* pro careers for earlier classes: BBGM's own ratings and stats for each mapped pid. Those replace the projected pro tail in the Hall, the hindsight redraft and comparables (Q17, Q28). The world's "what happened to him" becomes fact.
*Hooks:* the functions above; app.js `looksLikeLeague` 4411; universe.js `fileFingerprint` 4484 and `registryOf` 3162.
*Risks:* The same class appears in consecutive exports with BBGM's development applied, so its file fingerprint changes. Match classes by their pid set and draft year, not by fingerprint. League exports are large, so reuse the existing size caps and streaming read. Pids are stable inside one league but not across a re-import. The universe export needs a new version, v4, holding the pid map.
*Depends on:* F2 (optional), F4 (the projection to fall back on). *Size:* 6-8 days.

**F8. What-if results: force a game and replay what follows.**
*Sketch:* `cfg.resultOverrides = {"ncaa|East|R64|3": "Saint Peter's", ...}`, kept in the URL like locks. When a forced postseason game is played, the score is drawn exactly as now (so the RNG stream is consumed identically) and then mirrored when the wrong side won. Everything after it re-simulates: later rounds, the champion, awards, stock and notes. March re-sims cost about 90 ms (README, March upsets row), so this is interactive. Version 1 covers postseason games only. Version 2 adds conference-tournament finals (auto bids change the field). Regular-season forcing is out of scope because it changes the whole season.
*Hooks:* engine.js `resetPostseason` 3357, `phasePostseason` 3369; tournament.js `simulate` 210 and `simulateNit` 459 (each game goes through `T.playGameScore`); app.js `encodeConfig` 3976 / `linkPayload` 4079; the bracket UI (views.js `gameNode` 5438) gets a "make him win" control.
*Risks:* An override that names a team no longer in that slot after an upstream change must be dropped visibly, as locks are (`reportUnmatchedLocks`, app.js:4870). Golden hashes must not move when no overrides are set. The Play tab must not let an override leak answers, so disable it while a game is open.
*Size:* 3-4 days.

**F9. Box scores for the whole roster.**
*Sketch:* The game page deliberately shows only prospects' lines (views.js:8751: "rotation carries season averages, not per-game lines"). Generate per-game lines for returners and fillers lazily, once per team-season, the first time a team or game page asks. Allocate each game's team box (points, rebounds, assists and the rest, already on the team via `teamBox`, stats.js:3260) minus the prospects' lines among the rest of the rotation, by their season averages with seeded noise. The integer apportioning reuses `apportion` (engine.js:6577), and each man's season sums are held to his printed averages (a reconcile pass like `reconcileTeamTotals`, stats.js:3824). *Hooks:* `t.fieldPlayers`, teams.js `makeFiller` 201 / `capFillers` 307, stats.js `gameLog` 3995, views.js `gamePage` 8697.
*Risks:* Memory: 364 teams × 31 games × about 8 men, so keep it lazy and per team. A double constraint (game totals and season averages) needs an iterative fit. It must never feed back into awards or the board, which are calibrated on the current model.
*Size:* 4-5 days.

**F11. Game flow for featured games.**

*Hooks:* teams.js `playGameScore` 1701; stats.js `gameLog` 3995; views.js `gamePage` 8697; news.js buzzer-beater and overtime-classic kinds.
*Risks:* A constraint sampler that fails visibly on edge cases (an overtime game with an exact final, a foul-out). Scope it to featured games only, a few dozen per season, generated on demand.
*Depends on:* F9, Q8. *Size:* 6-8 days.

## 11. Robustness and responsiveness

**Bottom line.** The app has no memory leak, and its error reporting is mostly sound: a global `error`/`unhandledrejection` banner exists, and 40 rerolls and two 10-season universes produced no page errors. It still feels clunky for three reasons, all measured:

1. **The whole engine runs on the main thread as one long task.** A reroll, a slider release or a universe season freezes the page for the full run. 80% of a reroll is the engine and 3% is rendering.
2. **Every `render()` pays a fixed tax that has nothing to do with the view.** The archetype sidebar is repainted with an O(n²) lookup, then forced layouts follow. In universe mode a 566 KB localStorage write is added on top. This tax is about 70% of a tab switch and about 70% of every slider `input` event.
3. **One sub-step does most of its phase's work.** About 80% of the postseason phase is the 15-week AP poll, which recomputes NET from scratch 14 times. It also sits in the wrong phase, so "March upsets" re-runs it for nothing.

Most of the fixes are small and local (P1, P3, P6, P7, P9). Moving whole runs to the worker (P5) is the one large item, and the measurement below shows it is feasible: a full result structured-clones in about 1/20 of the time it takes to compute.

**Measurement caveat.** The container was shared with other audit passes: 4 vCPU, load average 30–38 throughout. A fixed calibration loop (5e7 iterations) took 190–420 ms here against about 60 ms on an idle desktop, and `node tools/bench.js` gave a cold run of 5.3 s against the README's 550 ms. **Divide absolute wall-clock numbers by roughly 5–10.** Ratios and profile shares do not depend on load, and the recommendations rest on those. Harness scripts are in `scratchpad/s11/` (perf1–perf8.js, agg.js, *.cpuprofile).

### P1. `paintArchWeights` is O(n²), runs on every render and every slider tick, and dirties the sidebar
- **Status:** MEASURED.
- **Where:** js/app.js:1992–2017. The hot line is 2011: `RB.ARCHETYPES.filter((x) => x.name === i.dataset.arch)[0]` for each of about 385 inputs, so roughly 148k comparisons. It also calls `archFilterHook` (applyArchFilter, js/app.js:3725) and rewrites 385 `textContent`/`value`s. Called from `paintConfig` (js/app.js:1730) and `render` (js/app.js:9095).
- **Numbers:**
  - In the tab-switch profile it is 45% of `render()` (996 of 2194 ms; the 2011 lambda alone 694 ms).
  - In universe mode it is 40%.
  - It is 70% of the slider handler (569 of 811 ms over 20 events).
  - A/B with the panel removed: Universe tab 87 → 26 ms, Play tab 83 → 10 ms, slider median 43 → 25 ms.
- **Fix:**
  1. Use the `byName` map that already exists at js/app.js:3723 instead of the `filter` (O(n)).
  2. In `render()`, repaint only when `res` or `cfg.archetypeWeights` changed (cache the last pair).
  3. In `paintConfig`, skip it unless the moved key is an archetype weight.
  4. Write `value`/`textContent` only when the value actually differs.
- **Expected gain:** about 60–70 ms (loaded), or about 10–15 ms idle, off every render and every slider event. That is −40–45% of light-tab switch time and −40% of the slider handler.
- **Effort:** S.

### P2. Slider drags start a full engine run mid-drag, and each `input` repaints the whole settings panel
- **Status:** MEASURED.
- **Where:** js/app.js:3362–3369 (the `input` handler runs `pushUndo`, `paintConfig()` and `scheduleRun()` each time) and js/app.js:3969–3972 (`setTimeout(run, 140)` trailing debounce).
- **Numbers:** In a 30-step drag with one 300 ms pause, the handler took 35–224 ms per event, which is already over the 16 ms frame budget. A 6 269 ms long task fired **during** the drag and another 4 937 ms one at the end.
- **Fix:**
  1. While the pointer is down (the `pointerdown` flag is already tracked at js/app.js:3361), do not schedule a run; run on `change`/`pointerup`. Keep the 140 ms debounce for keyboard steps only, or raise it to about 400 ms.
  2. Throttle the visual repaint to one per frame with rAF, and repaint only the moved control's label and badge instead of all of `paintConfig()` (see P1).
- **Expected gain:** No run starts mid-drag. A drag goes from 6 s+ of freezes (loaded) to one run at release. The handler drops to the 1–3 ms range idle.
- **Effort:** S.

### P3. The AP poll lives in the postseason phase and rebuilds NET from scratch 14 times
- **Status:** MEASURED (profile) and VERIFIED (dependencies, by reading).
- **Where:**
  - js/engine.js:3382–3383 calls `RK.computeRankings` and `RK.weeklyPoll` inside `phasePostseason`. Their only inputs are regular-season games (`regGames` filters `stage === "reg"`, js/rankings.js:29), the team ratings and `rng.child("appoll")`. Children are seed-derived (js/rng.js:148), so the draws do not depend on order.
  - Inside them: js/rankings.js:426 `netByWeek` re-solves `netScores` per week; js/rankings.js:41 `computeStrength` does a Map lookup and a binary search **per game per pass**; js/rankings.js:115 `computeAdjEff` iterates up to 400 times from cold every week.
- **Numbers:** `weeklyPoll` is 19.5% of a cold run and 17.8% of a universe season. `phasePostseason` is 24.6% in total, so the poll is about 80% of that phase.
- **Fix:**
  1. Move `computeRankings` and `weeklyPoll` to the end of `phaseRegular`, or cache them keyed on the regular phase's output. The postseason-only knobs (`upsetFactor`, `coachTurnover`, `weirdness`) then stop paying for them. Fingerprints are unchanged because the rng child is name-derived; check with `tools/golden.json`.
  2. In `computeStrength`, precompute an `Int32Array` of opponent indices once, and compute each team's percentile once per pass (364 binary searches instead of about 11k).
  3. Warm-start `computeAdjEff` from the previous week's ratings.
  4. Reuse arrays instead of allocating Maps and `filter()` copies per week (GC is 10%).
- **Expected gain:**
  - The "March upsets" row (postseason → …) gets about 20% of a full run cheaper, roughly −35–45% of that row.
  - A cold run, reroll or universe season: −12–15% from items 2–4.
- **Effort:** S for the move, M for the solver work.

### P4. A universe season is one uninterruptible long task
- **Status:** MEASURED.
- **Where:** js/app.js:7541–7578 (`step(k)` calls `chain.step(k)` synchronously, then `setTimeout(step, 0)`). `beginChain` also runs `previewClass` for every file up front (5%).
- **Numbers:** 10 seasons gave 19 long tasks of 4.9–8.9 s and a 12.8 s maximum event-loop lag (about 0.6–1 s and 1.5 s idle). Stop, tab clicks and scrolling are serviced only between seasons. `render()` runs after every season because each season takes longer than `UNIVERSE_RENDER_MS` = 300 (js/app.js:7285), so P1's tax is paid on every season too.
- **Fix:** Give the runner a stepping API, for example `runner.runSteps(cfg)` returning an iterator that yields after each phase (js/engine.js:5342 already loops over `PHASES`). Drive it with `setTimeout`/`scheduler.yield()` between phases. A finer option is to also yield inside `buildPriorSeasons` per program. P5 is the real fix.
- **Expected gain:** The longest task becomes the stats phase, about 36% of a season, and about 28% once P3 is done. That cuts it from about 0.8 s to about 0.25 s idle, and Stop responds within a phase.
- **Effort:** M.

### P5. Rerolls and universe seasons could run in the worker; the premise that they cannot is outdated
- **Status:** MEASURED (clone cost) and UNVERIFIED (behaviour after a round trip).
- **Where:** The comments at js/app.js:5695–5700 and js/worker.js:20–24 say the result is "a graph of live objects, not a message". `structuredClone(state.results[0])` succeeded with **no un-cloneable keys**, in 194–262 ms against a 4–7 s run on the same box (about 1/20). Structured clone keeps cycles. It drops prototypes and functions; I did not check whether any view calls a method on a result object.
- **Fix:**
  - Keep a second runner in the worker for **full** runs: reroll, Reroll-until's final apply, and universe chains. Post `{leagueFile once, cfg}` and receive the result.
  - Keep the main-thread runner for staged partial re-runs, and seed its phase cache from the received result, or simply let the next staged change cold-run.
  - A cheaper interim step: speculatively pre-compute the *next* reroll seed's result in the worker while the user looks at the current class, and swap it in on click.
- **Expected gain:** A reroll goes from about 600–900 ms frozen to about 20–40 ms of main-thread deserialisation, which matters for INP. A universe stops freezing the tab altogether.
- **Effort:** L.

### P6. `persist()` writes the entire state (up to 567 KB) synchronously on every tab switch, plus an IndexedDB autosave
- **Status:** MEASURED.
- **Where:**
  - js/app.js:8911 (`showTab` calls `pushNav(); persist(); render();`).
  - js/app.js:3952 (every `<details>` toggle calls `persist`).
  - js/app.js:345 (`JSON.stringify(payload())` including `universeForStorage()`).
  - js/app.js:8096–8109 (`scheduleAutosave`, 600 ms later, calls `slotRecord` and then IndexedDB `put`, a structured clone of the universe, even when it has not changed).
- **Numbers:**
  - `persist()` is 66 ms per call at 10 seasons (loaded).
  - In the universe tab-switch profile, persist is 13% of `showTab`, `setItem` 292 ms, and autosave and `slotRecord` about 300 ms over 24 switches.
  - The single-class payload is still 152 KB.
- **Fix:**
  1. Coalesce `persist()` into one write per idle period (`requestIdleCallback` with a 1 s timeout), and flush on `pagehide`/`visibilitychange`.
  2. Store the universe under its own key, written only when a `universeVersion` counter changes (chain finish, import, rename). The same dirty check gates `scheduleAutosave`.
  3. Store `tab` and `open` groups in a tiny separate key.
- **Expected gain:** −10–15% of every universe-mode tab switch (about 66 ms loaded), and no IndexedDB churn when nothing changed.
- **Effort:** S–M.

### P7. Forced layouts and a rebuilt tab strip on every render
- **Status:** MEASURED.
- **Where:**
  - js/app.js:8967–9000: `#tabs` is emptied and 12 buttons rebuilt with 24 listeners on every render.
  - js/app.js:9001–9010: `tabs.scrollWidth`/`getBoundingClientRect` are read, which forces layout #1.
  - js/app.js:9109–9115: `captureScroll` reads scroll positions.
  - js/app.js:9118–9136: `restoreScroll` writes `view.scrollTop` and reads `global.scrollY` straight after `view.innerHTML` is rebuilt, which forces layout #2.
- **Numbers:** In the tab-switch profiles, `restoreScroll` is 28% of `render()` (single class) and 30% (universe). Most of that is layout invalidated by P1's sidebar writes.
- **Fix:**
  1. Build the tab strip once and only toggle `.active`/`aria-selected`.
  2. Do the "scroll active tab into view" check only on a narrow viewport, inside rAF.
  3. In the `saved.top` case call `scrollTo(0,0)` without reading `scrollY` first.
  4. Do P1 so the sidebar is not invalidated.
  5. Use a delegated click handler on `#view` instead of per-row listeners.

  Adding `contain:strict` to `#settings` gave no measurable gain in an A/B; P1 is the lever.
- **Expected gain:** About −20–25% of each render after P1.
- **Effort:** S.

### P8. Opening the editor, sorting, or typing a filter rebuilds the whole view; News is rebuilt every visit
- **Status:** MEASURED.
- **Where:**
  - js/app.js:9013 (the comment says "Every interaction rebuilds this view from scratch") and `view.innerHTML = ""` at js/app.js:9041.
  - js/views.js:3860 calls `News.build(res, …)` with no cache. js/news.js:8181 runs `runTemplates` every time, including after each debounced filter keystroke.
- **Numbers:**
  - Row click → editor: 400–450 ms to frame, 6.4k elements.
  - Sort click: 198 ms.
  - The News tab is the heaviest single view: 288–463 ms. `viewNews` and `build` are 4.6% of the tab profile, about 170 ms per visit loaded.
- **Fix:**
  1. Memoise `News.build` in a `WeakMap` keyed by `res`, sub-keyed by the `followed` value, as `proCache`/`mockCache` already do at js/views.js:6789/6813.
  2. Open the editor by inserting or replacing only the editor panel node, and sort by reordering existing `<tr>`s. Both are incremental; keep the full rebuild as the fallback.

### P9. Input queued during a long task replays afterwards and starts extra rerolls
- **Status:** VERIFIED.
- **Where:** js/app.js:7055 (guards on `busyDepth`, which is 0 again by the time queued events are dispatched) and js/app.js:12958 (the `r` key). `BUSY_BUTTONS` (js/app.js:5706) only get `aria-busy`, not `disabled`, and `body.busy` only changes the cursor (css/style.css:869).
- **Numbers:** Pressing `r` three times while a reroll was running produced **2** rerolls. A double-click inside the pre-rAF window produced 1, which is correct.
- **Fix:** Record `busyEndedAt = performance.now()` in `endBusy`. In the reroll, Re-apply and Until handlers and in the global keydown handler, ignore any event with `e.timeStamp < busyEndedAt` (it was queued while frozen). Optionally set `disabled` for the busy duration.
- **Expected gain:** No surprise second class or lost undo slot after impatient clicks.
- **Effort:** S.

### P10. Re-apply has no busy guard
- **Status:** MEASURED.
- **Where:** js/app.js:12625: `$("btnRerun").addEventListener("click", () => run())`.
- **Numbers:** Five quick clicks queued 5 `withBusy` callbacks, which meant 5 runner calls and 5 full renders (1.0 s loaded when cached). The first Re-apply after a setting change cost 4.7 s, so 5 clicks then would cost 5× that.
- **Fix:** Use the same `busyDepth > 0` early return that `reroll` has, or coalesce `run()` calls with a pending flag.
- **Effort:** S.

### P11. When the batch worker crashes, the batch silently restarts from zero on the main thread
- **Status:** VERIFIED.
- **Where:** js/app.js:12178–12181: `batchWorker.onerror` calls `runBatchInline(file, cfg, n)` with `i = 0`, and js/app.js:12215 overwrites `batchPartial`.
- **Numbers:** A simulated crash at class 3 of 6 threw away 2 finished rows, then ran all 6 inline: 6 long tasks of 3.6–5.9 s, 46 s total, and an **empty status line**.
- **Fix:**
  1. On `onerror`, respawn **one** fresh worker and resume at `batchPartial.length`, using the same `base#i` seeds so the rows stay identical.
  2. Fall back to inline only if the respawn fails, and resume from the same index there too.
  3. Write a status message ("worker stopped; continuing on this tab").
  4. The same pattern applies to the search worker (js/app.js:6517–6521, `startInline()` from try 0).
- **Expected gain:** A crash costs one class, not the whole batch, and the page stays responsive.
- **Effort:** S.

### P12. Search-worker failures are swallowed or never detected
- **Status:** VERIFIED (by reading).
- **Where:** js/worker.js:60 and js/app.js:6467: `catch (err) { /* a failed candidate is just not the one */ }`. If the engine throws for *every* candidate under some settings, the user is told "no match in 60 tries" after 60 wasted runs. There is also no watchdog: a worker that dies without an `error` event (for example an OOM kill) leaves "Cancel 23/60" up until Esc.
- **Fix:**
  1. Count failures, return `{failed, firstError}` in `searchDone`, and show the error when `failed > 0`.
  2. Abort after 3 consecutive failures.
  3. Add a watchdog that treats no `searchProgress` for more than 10× the median per-try time as a crash and goes to the P11 path.
- **Effort:** S.

### P13. Service worker and update flow: page/worker version skew, and network-first with no timeout
- **Status:** VERIFIED (by reading); not exercised, because the SW is disabled under webdriver (js/app.js:12359–12364).
- **Where:**
  - sw.js fetch handler: network-first, `skipWaiting` + `clients.claim`.
  - js/worker.js:17–18: `importScripts` of the current engine from the network.
- **Problems:**
  - (a) A tab opened before a deploy keeps the old engine in the page. Any batch or "Reroll until…" started after the deploy spawns a worker with the **new** engine, so a seed found by the worker is replayed by the old page engine and may not satisfy the clause. Batch rows also no longer match the page.
  - (b) On a flaky network ("lie-fi"), each of the ~33 requests waits for the network to fail before the cache answers, so an offline-capable start can take tens of seconds.
  - (c) There is no "new version available" prompt.
- **Fix:**
  1. The worker reports `Universe.ENGINE_REV` in its first message. On a mismatch, the page falls back inline and shows "a new version is available — reload".
  2. Race `fetch` with a 3 s timeout before falling back to the cache.
  3. Listen for `controllerchange` and offer a reload.
- **Effort:** S–M.

### P16. Universe memory ceiling
